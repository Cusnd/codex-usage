# 云端到浏览器：最快路径探索

2026-09-13。用户明确关注“打开页面或刷新时等太久”。本轮只做代码/历史请求审计、隔离协议原型和真实浏览器接收端实验，**没有修改生产实现，也没有部署**。当前工作树包含 9 月 12 日尚未部署的优化；历史线上计时仍按当日版本解释。

## 结论与建议顺序

对用户的页面等待，优先方案是：**页面直接取得新的固定版本统计，完整离线镜像在后台继续同步；日常刷新走增量，首次全量采用带正文的快照；浏览器以新代次保存正文，验证完整后切换指针。** 继续扩大 manifest 页数能减少部分往返，但保留了页面等待镜像、清单与正文分开传、正文二次写入这三项成本。

| 优先级 | 建议 | 解决的等待 | 实施边界 |
| --- | --- | --- | --- |
| 0 | 先定位并修复定时版本清理的 D1 CPU 重置异常 | 健康检查也会超时或返回 500 | 本轮已从线上日志定位到 cleanupVersions 调用，尚未证明具体慢 SQL；修复后再建立健康线上端到端对照 |
| 1 | 在线 query cut 与实体 mirror cut 独立，首屏查询优先，镜像后台继续 | 已有缓存时刷新仍等完整镜像才能显示新数值 | 所有卡片必须共享同一新 cut；旧镜像的项目名不能混入新页面，删除代次和用户隔离仍约束查询 |
| 2 | 同 cut 普通刷新快速结束；未筛选范围优先现有 inline delta | 已有全部数据却反复重扫 manifest | 完整校验保留为明确操作或周期任务；设备范围需要正确的范围差集，不能直接套用全用户 changes |
| 3 | 首次完整同步直接下载带正文的压缩快照，大页或有界连续流 | 数百次清单/正文往返、重复元数据及重复压缩字典 | 维持固定 cut、范围、逐实体 hash、数量、断点和终结验证；完整前不得提升 coverage |
| 4 | 临时新代次写入一次，完整校验后原子切换 active 指针 | IndexedDB 从 staging 再复制全部正文到正式区 | 仍需实现增量覆盖层、旧代次回收、跨标签删除和迁移；回收成本是延后处理，不是消失 |

这四项可以组合，分别缩短页面等待、日常更新、首次传输和本地落盘。它们的实验时间不应相加或相乘作为线上端到端成绩。

## 等待在哪里

当前 `queryLeaseOf()` 优先返回完整旧 `activeLease`；只有完全冷启动时才允许使用正在建立的 baseline lease。`mutate('refresh')` 又等待 `controller.trigger('manual')`，而 manual 默认重建 full baseline。因此上轮的冷启动提前查询没有完整覆盖“已有缓存，点击刷新”的情形。

当前统计查询直接使用服务端或 `query_results`。浏览器没有扫描全部 entity 缓存来计算图表；完整实体主要用于镜像恢复/核对、可选项目名称回退和底层 entity API。用户指南也明确，完整实体缓存不代表任意未打开筛选均可离线计算。因此可以保留现有完整镜像承诺，同时让页面更新独立完成。默认取消完整镜像属于另一项产品取舍，不纳入本报告的完整同步加速结论。

对 9 月 12 日已保存的线上记录重新按读取过程拆分：

- 一个 manual-recovery **117.944 秒观察窗口**包含 118 次 manifest，串行在途区间合计 111.938 秒，占 94.9%；只需 5 次实体请求、6,758 字节。该窗口包含后续自动轮次，不能把它称为严格的一次按钮刷新用时，但能证明大量时间用于核对已有内容。
- 新单设备缓存为 **1,015 个实体**。recent 与 full 的期望数量完全相同；第二段仍用 **7.923 秒、6 次 manifest**，没有下载实体。在页面查询已与冷实体下载分开后，这类重复 recent/full 校验值得取消；若仍需要优先获得近期离线覆盖，则应保留有明确收益的近期策略。
- 当前已有下一页 manifest 预取，不再把它算成新方案。changes 本来就内联完整实体与删除引用，也无需重做一次“changes 内联”。

详见[请求窗口与调度分析](../cloud-request-analysis-20260913/request-analysis.md)和[浏览器合同与数据源审计](browser-design.md)。

## 相同完整数据的传输原型

隔离的本地 Workerd + D1，25,000 条事件和 250 条线程，共 **25,250 个实体**，正文约 14.14 MB。四条路径均经过相同生产 versionGate、会话鉴权、scope/lease 检查，使用同一固定版本、gzip 和 keep-alive。每种模式各三次，顺序为正/反/正；输入准备和 lease 创建不计时。下表是最终公平重测 `parity-final` 的中位数。

| 传输方式 | 完成耗时 | HTTP 请求 | D1 SQL 条数 | gzip 正文字节 |
| --- | ---: | ---: | ---: | ---: |
| 当前 manifest 500 + entities 100，正文并发 2 | **3,911.1 ms** | 304 | 2,381 | 3,661,905 |
| 正文合并页，最多 1,000 条 / 1 MiB | **798.9 ms** | 26 | 208 | 2,487,363 |
| 正文合并页，最多 5,000 条 / 4 MiB | **596.1 ms** | 6 | 48 | 2,474,424 |
| 有界 gzip 流，每批查询 1,000 条 | **707.9 ms** | 1 | 135 | 2,479,350 |

在这个完整全量样本中，5,000 条合并页完成时间约为当前路径的 **1/6.56**，减少 **84.8%**，gzip 正文字节减少 **32.4%**。它是本轮测到的最快传输候选；单条流请求最少，但本地计时并非最快。该流样本首响应字节约 570 ms，大页约 99 ms，压缩缓冲/输出节奏仍需调整；不能因使用 stream API 就声称浏览器已提前处理所有批次。

计时客户端是 Node HTTP + gzip 解码，完整响应收集后解析；这不是浏览器的网络到 IndexedDB 端到端测试。表中包含本地服务端/传输/客户端解码耗时，不包含 Chrome hash 校验与落盘；真实跨地域 RTT、带宽、Cloudflare 托管 D1、较大实体与内存峰值需另测。gzip 已同时用于对照，收益不能全部归因于“新增压缩”。完整 Workerd 进程 CPU、内存不等于 Worker isolate 的配额计数或峰值。

所有完整样本的排序实体正文摘要和数量完全一致；检查了超安全整数 token 字符串、固定旧 cut 在新 head 发布后仍可读、匿名 401、版本不符 426、跨用户与过期 409、字节预算、单实体超预算明确失败、gzip 读取中断后续传拼接完整 hash，以及删除版本变化后不发送完成标记。更多范围和 10k 输入的 72 条早期探索样本保留，但其候选当时缺少 versionGate；**最终性能对比仅使用修正后这 12 条公平样本**。

实现、复跑说明和完整限制见[服务端原型报告](server-report.md)。最终原始证据：`artifacts/sync-fast-path-20260913/server/parity-final.json`、`parity-final-summary.json`、`checks.json`。本地服务已停止，未使用线上 D1 写入或生产路由。

## 浏览器接收端实测

CUA 控制 Windows Chrome 152，在独立 loopback 测试页运行生产 `verifyEntities` 和 `IndexedDbCloudCache`，没有使用 Playwright。固定 **25,000 条合成事件**，每条包含结构化字段、超安全整数范围的十进制 token 字符串和 512 个确定性十六进制字符；所有候选使用完全相同的实体。时间包括 hash 校验、暂存/写入和完整提升，**不包含网络、服务端构建、输入生成、正确性读回或测试数据库清理**。

先做 100 与 1,000 条事务批次的三对 AB/BA/AB 实验：完整导入中位数为 11.466 → 10.137 秒，样本随轮次有明显漂移。仅扩大批次没有消除耗时数秒的全量复制，不能将这组数据外推为稳定的线上加速率。

随后在同一轮配对实验中比较当前缓存与独立 shadow-generation 原型，每个候选各三次：

| 指标，中位数 | 当前缓存，100 条批次 | 新代次原型，1,000 条批次 |
| --- | ---: | ---: |
| 完整导入 | **10,810.7 ms** | **5,485.9 ms** |
| 逐实体 hash 校验 | 500.2 ms | 562.2 ms |
| 写入/暂存 | 4,657.5 ms | 4,389.5 ms |
| 最终提升，含计数/封存 | 5,682.6 ms | 448.1 ms |

完整导入耗时约减少 **49.3%**。主要收益来自正文只写一次；新代次也保留物理数量校验，所以完整提升仍要约 448 ms，不能把单次指针赋值的毫秒数当作全部提升成本。各阶段的独立中位数不保证相加等于总时长中位数。

六次导入均完整逐字段等值，精确 token 字符串不变，损坏内容 hash 被拒绝。新代次原型另验证：构建期间旧代次样本可读、未完整不能切换、错误 CAS 版本不能切换、完成后旧代次样本保留。原型尚未实现生产的增量 overlay、GC、跨标签 reset/删除协议和旧存储迁移；当前结果证明接收端结构有优化空间，不能称为已可发布的缓存后端。

原始记录为 `artifacts/sync-fast-path-20260913/browser-import.json`、`browser-shadow-comparison.json`；[汇总脚本](summarize-browser.mjs)复核样本完整性并输出 `browser-summary.json`。测试标签页已关闭，18914 本地服务已停止，记录为 `browser-cleanup.json`。

## 更高上限与平台约束

首次全量的长期候选是**预先生成私有压缩分块快照 + 增量尾部**：服务端生成一次固定版本对象，多次下载复用，避免每个浏览器反复让 D1 枚举相同历史。R2 支持有条件读取与 Range，可以支撑不可变对象和断点。单个 gzip 的任意偏移不等于可独立解压的实体边界，实际应使用独立压缩块或明确的可定位格式。[R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)

R2 的新组件、生成任务、存储与回收都有成本；本轮未部署或测量真实 R2，不能把这一架构候选称为已经证明的最快线上方案。也不能通过公开对象地址绕过身份和删除检查：R2 本体强一致，但启用 CDN 缓存后删除对象可能仍命中旧缓存，需保持私有鉴权与删除版本控制。[R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/)

单纯增加大量并发也不是无条件收益。单个 D1 数据库逐个执行查询，过多请求会排队；减少请求和 SQL 工作量比无限加并发更有依据。[D1 limits](https://developers.cloudflare.com/d1/platform/limits/) Worker 流式处理可以避免将整个大对象缓冲在 128 MB isolate 内存中，但数据查询、解析和压缩仍需有界；完整 Workerd 进程内存不等于 isolate 内存峰值。[Workers Streams](https://developers.cloudflare.com/workers/runtime-apis/streams/)

浏览器还有“直接保存压缩块 + 范围索引 + active 指针”的候选，可进一步减少逐实体写入次数。它要求新的缓存后端，单实体读取要解压对应块，增量、内存、断点、完整性和删除仍需设计。**本轮没有测量该方案**，不把它排为已证实最快。

## 下一轮实施与验收

本轮结束前的线上只读检查发现可用性异常：2026-09-13 05:03–05:05 UTC，三次公开 health 检查依次为 **500（8.71 秒）、15 秒超时、500（1.74 秒）**。随后 D1 的 SELECT 探测返回错误 7429：`D1 DB exceeded its CPU time limit and was reset.`。这个返回不能证明该微小探测语句就是耗时来源。

进一步对 04:55–05:10 UTC 的 Workers 日志作不持久化只读查询，返回三条采样异常，堆栈均为 `cleanupVersions (index.js:9096:115)` → `scheduled (index.js:18168:5)`。这是版本清理调用涉及 CPU 重置的直接证据；采样条数不是全部失败次数，也尚未把具体清理 SQL 证明为根因。当前线上 Worker 版本仍是 `29db4b4d-d328-416a-956d-eac4475d530e`，部署时间 2026-09-12T13:54:49.285381Z，source `044daa3ee280c4a591130cb5baabf8a55bcaf6da`，没有部署本轮原型。证据保存于 `production-health.json`、`production-health-recheck.json`、`production-diagnostic.json`、`production-worker-errors.json`（均在本轮 artifacts 目录）。

代码审查发现一个优先候选：`modules/sync/reads/cleanup.ts:10` 每分钟对五张表执行旧 epoch 删除，使用关联域条件、两个 NOT EXISTS 和 LIMIT 1000。这里 LIMIT 只限制命中的删除候选数量，不能保证扫描量有界；即使没有旧 epoch，也可能扫描大量当前历史行。当前 bundle 的该 await 在第 115 列，与线上堆栈列号吻合，但没有线上 source map，不能据此唯一定位具体表或断言根因。下一步应只在本地对原 SQL 做 EXPLAIN 和全部为活跃 epoch 的规模夹具，逐表测扫描量，再比较显式旧 epoch 工作队列、持久游标和扫描预算。不要在故障线上反复运行清理作为诊断。

清理路径的逐项审查与建议夹具见 [cleanup 只读审查](server-cleanup-review.md)。因此下一轮首先在本地定位/复现历史版本清理的 SQL 工作量并准备有界修复；线上恢复健康后，取得稳定端到端基线。页面体验先实现前台 query cut 独立和日常增量；随后一起接入新的快照协议与缓存代次，保持原 UI、完整云端历史和后台完整镜像。前台“页面已更新”与“完整离线缓存已就绪”分别报告真实状态。

验收用相同输入、范围和版本，至少覆盖无变化刷新、小量新增、同实体多次更新、全空缓存、设备范围移入/移出、删除、过期变化日志和中断恢复。分别记录页面新统计可见、最后内容到达、全部校验和缓存提升时间；完整实体和查询逐字段一致。线上目标需在同源页面/后端部署后复测，不能用当前独立实验相加得到一个承诺秒数。

本轮所有新文件均为 `experiments/` 或被忽略的 `artifacts/` 下的探索材料；生产实现保持上轮状态。没有执行 commit、push、部署或远程迁移。
