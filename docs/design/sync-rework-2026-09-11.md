用户此前指出：原先本机方式是为了效率，引入云端后新增路径使同步体验很慢；应认真设计便于存储、解析和传输的数据结构，不能只调 UI 或讨论下载频率。该问题说明此次改造的性能要求，不替代上述根目标。

以下术语与分段表保留最初讨论时的分工；处理位置的后续修正见 3.9–3.10 节，当前实验进度见 3.24–3.29 节。

本讨论将参与端区分为：

| 名称 | 含义与职责 |
| --- | --- |
| 采集端 | 安装 Node.js 后台服务的电脑；持续低干扰采集、增量解析、本机存储与显示，独立向云端上传 |
| 云端后端 | 接收和持久保存数据，对访问端提供数据；采集电脑关机后仍可读取已同步历史 |
| 访问端 | 访问云端页面的机器及其浏览器；用户最初说“到本地再解压或解析”中的“本地”指这里 |

“同步”不得再含混指代所有阶段。性能设计和计时至少区分：

1. 原始日志发现与增量读取。
2. 原始记录的语义解析、去重、标准化。
3. 已解析结果编码、压缩与上传。
4. 云端解码、校验、应用数据和更新索引。
5. 访问端从云端下载、解压、解码和写入缓存。
6. 页面查询、聚合与展示。

用户认为解析是优化重点，要求设计合适的数据结构。最初讨论时尚未做分段性能测量；后续测量已经完成并记录于第 3 节各实验条目。各段证据须按输入和计时边界解释，不能仅依据早期假设认定整个系统的最大瓶颈。

## 3. 已明确确认的要求

### 3.0 继续讨论后的最新决定：保留原有使用逻辑，替换数据来源

用户在读取存档继续讨论后明确：

> 全流程分为-采集端采集，转为我们设定的数据结构，然后通常是实时传递到云端，然后本地再根据用户设置来从云端同步

> 原先的是本地读取json，现在只是变为了读云端的数据，该怎么样就怎么样，我最新的决定是这样的

这是本轮最新架构决定，优先于此前对访问端计时器与实时更新关系的候选解释：

```text
采集端读取 Codex 原始记录
    → 转成约定的标准数据结构
    → 通常实时传递到云端后端并保存
    → 访问端按用户设置自动同步，或手动同步
    → 本地缓存、查询、统计和展示
```

- 本段用户所说的“本地”是从云端同步数据的访问端；采集端仍可使用自身解析结果供本机面板查询。
- 访问端沿用原有自动／手动刷新、间隔设置和数据使用逻辑；原来从本地原始记录获取数据，现在从云端后端获取标准数据。
- 采集端的采集、标准化和通常实时上传独立运行，不受访问端刷新间隔控制。
- 不另设绕过用户加载间隔的访问端实时更新通道；上一轮将这一点作为二选一的问题已经被本次决定解决，不再重复询问。
- 已确认的第一次近期、第二次全量、自动与手动共用进度、离线全量缓存等要求继续适用。
- “通常实时传递”保留为上传方向的要求，具体批量窗口、故障重试和性能指标在实现方案中说明；不能把它变成访问端无视用户设置的强制刷新。
- 本次明确的是需求和架构，没有批准开始修改实现。后续讨论应集中于标准数据结构、增量协议及必要的正确性问题，原有行为已有定义的细节默认沿用。

### 3.1 采集与云端历史

- Node.js 后台持续、低干扰采集；收集器与解析器职责分开。
- 先形成适合存储与解析的数据，再供本机面板使用，并定期向云端传送和保存。
- 采集端继续独立增量解析和上传；本机使用不应等待云端。
- 云端必须持久保存历史，不能依赖采集电脑一直开机。
- 用户已有 Workers Paid，可以讨论采用其他 Cloudflare 服务；尚未批准具体服务组合、资源创建或费用预算。

### 3.2 最新确认：访问端只从云端后端取数，不控制采集机器

用户最终选择：

> 访问端加载：控制页面从云端下载、入缓存；采集端继续独立增量解析和上传。

并明确补充：

> 对云端来说，唯一的来源就是云端的后端，也只应从云端的后端采集，不应控制其他机器，云端相当于数据中转站。

因此本轮采用以下边界：

- 访问端的数据入口是云端后端。
- 页面自动或手动加载，不直接访问其他机器，也不向采集机器下发补传、解析、刷新或其他控制指令。
- 采集端自行采集、解析、调度上传；访问端只能读取云端已经接收并可提供的数据。
- 若云端尚未收到某些历史，访问端不能声称该部分已完整加载，也不能通过远程控制采集端来补齐。
- 助手此前提出“手机点击刷新 → 云端选择 B → 指令 B 读取额度”的流程，不得继续作为默认设计。额度代读如何在不远程控制的边界下运行，见第 5 节。

### 3.3 自动／手动加载：第一次近期，第二次全量

用户澄清：这不是第一轮完成后立即自动开始第二轮，而是按两次触发执行，用于照顾希望手动提前获取完整历史的用户。

- 自动加载有计时器，间隔由用户调整。
- 手动按钮可以提前触发下一次加载。
- 自动与手动共用同一个初始化进度，不分别计数。
- 第一次加载活跃任务和最近 30 天。
- 第二次加载全部历史，不论这次由计时器还是按钮触发。
- 该两轮规则作用于**访问端从云端下载并写入缓存**，不控制采集端上传过程。
- 第二轮“全量”指形成完整历史覆盖，已经处理的数据应复用，不必重新解析或重新下载相同版本。
- 计时需要区分每轮下载、解码、入库、查询等阶段。

| 触发组合 | 预期 |
| --- | --- |
| 第一次自动，第二次手动 | 第二次全量 |
| 第一次手动，第二次自动 | 第二次全量 |
| 两次手动 | 第二次全量 |

以下执行细节目前是助手建议，尚未逐项确认：初始化进度持久化；首次成功完成后推进阶段；失败断点恢复；执行中再次手动点击登记下一轮而不并发重复处理；全量完成后日常只应用增量。

### 3.4 可见速度与近期优先

用户已选择以下验收目标：

- 正常在线、首次补采结束后，从 Codex 写出完整记录开始，本机通常 2 秒内、云端通常 10 秒内可见。
- 历史补传时，新事件仍优先。
- 首次连接大量历史时，活跃任务和最近 30 天优先，更早历史最终补齐。

上述数值是此前选择的性能目标，不是实测结果。最新决定（3.0 节）已明确：采集端通常实时上传，访问端按用户设置同步。因此访问端计时器调长后，展示随其下一次自动或手动同步更新，不另设独立的实时展示要求。

“通常”的统计方法、测试规模、资源约束和各阶段耗时仍需在验收方案中明确。此前“10 秒”的表述不能覆盖访问端用户主动设置的等待时间，也不能被当作已经获准的新调度机制。

访问端两轮加载不得被错误扩展为采集端也必须等待第二次按钮／计时器才上传旧历史。

### 3.5 离线与全量缓存

**最新优先级已调整，见 3.10 节。** 下列内容保留为此前讨论记录；不能再以完整离线分析或离线启动作为当前架构选择的硬性前提。全量缓存已解析结果与保存原始待解析数据是不同问题。

- 访问端支持断网查看已经缓存的历史，并应能离线启动应用。
- 用户选择**自动缓存全部已同步历史**，不是只缓存最近 90 天或浏览过的页面。
- 当前页面优先，历史缓存按上述两轮规则推进；空间不足时提示。
- 缓存应含支持任务、轮次、事件及关系查询的结构化数据，不能只有页面截图或汇总数字。
- 全量覆盖完成后可以离线查询完整缓存；未完成时明确覆盖范围，缺失不能当作零。
- 已发生的 Token 消耗和任务历史不能因关机、断网或本机清理原始日志而自动消失。
- 历史统计可以因去重、补齐和修正而更新；“历史保留”不意味着数字永远不可修正。

待定：缓存容量策略、是否允许自动淘汰及淘汰顺序、离线身份与退出行为、浏览器数据被清理后的恢复、覆盖清单的精确定义。

### 3.7 机器维度统计实际发生的消耗

用户明确选择：看的是某台机器**实际执行产生的 Token 消耗**，不是这台机器持有或上传的历史副本。

- 同一事件复制到另一台机器，不能计为另一台机器新增消耗。
- 一个任务跨机器继续执行时，归属需要细到事件，不能整项任务归给最后一台机器。
- 例如 A 消耗 100，复制到 B 后 B 新增 20：A 为 100，B 为 20，汇总为 120。
- 同一事件在全局只能计一次。
- 上传设备与执行设备必须分开记录。

当前鉴权已经能够识别绑定上传设备：`cloud/src/devices.ts` 的 `deviceAuth()` 按凭据查询设备，`cloud/src/usage-sync.ts` 将认证得到的 `device.id` 写入记录的 `device_id`。当前标准事件还没有独立的原始执行机器字段，因此必须区分字段缺失和设备鉴权失败。

正常在 A 产生、由 A 采集的记录应归属 A；候选设计是在标准事件产生时写入原始执行设备，后续中转、缓存或转发保留它。只有旧原始记录从未保存原始来源、又缺少可以恢复该来源的上下文时，上传设备才不足以证明执行设备，例如 A 的未标记原始日志被复制到 B 后首次上传。没有证据表明用户当前数据已经存在这种情况，不能将例外泛化为全部历史未知。

用户已经确认：对确实无法确定执行机器的旧记录，保留全局消耗、标记机器归属未知，支持带“用户指定”标记的手动批量归属。该兜底选择不代表用户认可正常上传设备不可识别，也不授权把原本能够确定来源的数据统一标成未知。

用户随后提出：采集器可以主动添加 UUID 或更好的标识，解析器本来就应通过采集器提供的数据进行解析和显示。后续设计采用“采集器先附来源标识、解析器继承、云端与访问端保留”的方向；具体候选为持久采集端 UUID 加来源代次／位置，并将设备、事件和批次身份分开，详见[协议补充](sync-protocol-contract-2026-09-11.md)。UUID 版本和字段实现仍是技术候选，并未获得开始修改产品代码的批准。

### 3.9 重新讨论解析位置：CF 与访问端浏览器之间的取舍

**本节浏览器优先的推荐已被 3.10 节修正。** 其推理把离线分析赋予过高优先级，并未充分区分原始解析、解析结果缓存和结果查询；不能作为最新推荐继续推进。

用户提出重新评估解析工作放在 Cloudflare 还是访问前端的浏览器，目标是平衡效率与成本，并避免把业务处理拆成一部分 Workers、一部分浏览器。**用户尚未选择处理位置，也未批准实施。** 此前“云端处理跨来源选优”等细节继续作为候选，不能视为本次已经确认的分工。

助手本轮建议：在保留完整离线筛选、查询和统计的前提下，将标准记录的业务处理集中到访问端浏览器。采集端仍负责读取原始 JSONL、来源标记和标准记录提取；CF 负责鉴权、格式校验、持久存储、版本及增量同步；浏览器统一执行跨来源事件去重、关系整理、统计和查询。同一套浏览器引擎用于在线缓存与离线缓存，不另建云端 Token 统计路径。这里区分原始格式提取与标准记录的业务计算；若用户所指“解析”包含全部原始格式解释，应先对齐该边界。

推荐依据与代价：

- 完整离线功能已经要求本地结构化缓存和计算能力；云端完成业务处理仍不能免除任意离线筛选的本地查询、聚合能力。仅缓存固定报表可以简化云端方案，但会改变已确认的离线能力。
- 浏览器端在每个独立缓存中承担首次下载、解码和建库成本；多台访问设备会重复这部分工作，弱设备上可能更慢。后续增量入库和受影响范围更新避免每次打开都全量重算。
- 使用一个浏览器 Web Worker 承担计算，UI 读取查询结果；持久存储完整历史，内存中仅保留有界批次。Web Worker 减少主线程占用，不消除下载、总 CPU、内存、存储配额及后台暂停方面的成本。
- CF 集中计算更适合在线为主、大量访问设备、要求弱设备快速首屏的场景；浏览器端更符合本项目已确认的完整离线、个人历史分析及避免双端统计路径的组合要求。这是架构判断，尚未完成同一真实数据集在目标浏览器与 CF 的对照测试，不能宣称已证明最优。
- 如果选择浏览器业务引擎，需要相应调整旧候选协议中云端 canonical_revision、跨来源选优和规范事件快照的归属；来源修订、幂等批次、完整覆盖和事务游标等正确性要求继续保留。不能只删除云端去重而遗漏访问端的对应职责。

本轮核对的官方成本事实（2026-09-11）：[Workers Paid](https://developers.cloudflare.com/workers/platform/pricing/) 最低 5 美元/月，包含 1,000 万请求与 3,000 万 CPU 毫秒，超额 CPU 为 0.02 美元/百万毫秒，换算额外 1 CPU 小时约 0.072 美元，仅指 CPU 项；不代表已核验用户当前套餐余量。[D1](https://developers.cloudflare.com/d1/platform/pricing/) 按扫描行数、写入行数和存储计费，索引写入也会增加写入量。[R2](https://developers.cloudflare.com/r2/pricing/) 不收出口带宽费，仍有存储和操作费用。因此不以“云端 CPU 一定昂贵”作为选择浏览器的理由，也不把浏览器计算视为没有设备和维护成本。

### 3.10 最新修正：在线优先，浏览器缓存已解析结果

用户指出：解析后的数据可以保存在 localStorage 或浏览器缓存中，没有必要存储原始待解析数据；应优先考虑有网使用，当前没有找到合适的离线访问产品场景。

据此修正前提：

- 在线访问是当前主要设计场景，不能继续要求用户围绕完整离线分析作选择，也不以独立离线引擎、离线启动或后台全历史重建作为架构的默认要求。
- 解析位置与缓存位置可以分开。CF 解析后，浏览器可缓存已解析的事件、任务、轮次、关系和查询结果；本地筛选或读取这些结果不等于重新解释原始日志。
- 浏览器不必保留一份原始待解析输入。原始资料的云端重处理策略是另一个问题，不能以此扩大浏览器缓存范围。
- 此前近期优先、后续全量的同步讨论不自动等于缓存原始日志；本轮不擅自取消已解析历史的缓存安排。

助手修正后的候选推荐：采集端自主增量采集、标记来源和封装必要记录；CF 集中承担业务解析、去重、关系整理及结果查询，持久保存结构化结果；浏览器按用户设置同步并缓存已解析结果、展示页面。CF 在数据变化时增量处理，查询使用已处理数据及可复用汇总，避免每次访问重新解析全部历史。浏览器缓存首先服务在线首屏、重复访问和减少下载；断网展示已有结果可作为附带能力，不为当前未成立的场景单独构建离线分析系统。

缓存介质候选：localStorage 用于设置、版本或小型结果；较多结构化历史优先考虑 IndexedDB。localStorage 的同步读写可能阻塞 JavaScript，IndexedDB 提供异步结构化存储，参见 [MDN Web Storage](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API) 和 [MDN IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)。这是缓存实现的选择，不影响“缓存 CF 已解析结果”的架构原则；尚未批准具体引擎或产品实施。

前一轮浏览器优先结论已撤回；CF 集中处理是基于最新前提的推荐，仍需用户确认，不能把纠正需求前提当成开始实施的授权。此前算法和协议实验只支持其原有测试范围，不能当作 CF 实际性能或账单证明。

### 3.12 Session、项目身份与用户分组：最新方向及同步候选

用户询问 session ID、项目名的来源，提出：稳定唯一标识可作为分组依据；工作路径变化按新项目统计，仍支持手工合并；合并操作先在访问端本地修改，再同步云端，并要求解释如何与解析更新协调。

本轮核对当前实现得到的事实：

- `server/importer.ts` 从 `session_meta.payload.id` 或 `session_id` 获取会话身份；显式消耗记录也可携带 `thread_id`。同一任务的多轮消耗使用同一个 session/thread ID，不能用该 ID 区分每一条消耗。
- 标题从 `session_index.jsonl` 中相同 `id` 的 `thread_name` 读取，并按 `updated_at` 选取更新记录；标题不作为身份。
- 项目归属从 `session_meta.cwd` 和后续 `turn_context.cwd` 获取，经 `projectPath()` 规范化；项目显示名是路径最后一段。当前统计代码没有从这些输入读取一个独立的 Codex 项目 UUID。
- 工作路径变化不保证 session ID 变化。使用当前 `Importer.consume()` 的纯内存合成检查：同一 session 的两轮分别在 `/work/alpha` 与 `/work/beta`，产生 100 和 20 Token，得到两个项目归属、同一个 session ID 和 120 的会话总量。该检查验证当前解析代码的行为，不证明所有 Codex 客户端产生日志的方式。

用户方向对应的候选模型：

- `session_id` 标识会话；`event_id` 标识可独立去重的消耗事件；`project_id` 标识项目实例；`group_id` 标识用户分组，名称均不参与身份判断。
- 由执行设备身份和规范工作目录确定项目实例，并通过统一映射分配、复用稳定 `project_id`，避免各浏览器各自随机生成同一个项目的不同 ID。工作目录改变产生新的项目实例；仅日志文件移动、上传路径改变、项目展示名改变，不改写历史事件归属。
- 同一项目可以有多个 session，同一 session 的事件也可以分属不同项目。按 session 查看仍聚合其全部有效事件；按项目查看依据各事件发生时的项目归属。若多个项目属于同一分组，session 数按 session ID 去重，不能直接相加各项目的 distinct 数量。
- 分组成员优先关联 `project_id`，因而原项目新增 session 也自动属于既有分组；新路径的新项目不会自动进入原分组，用户可手工加入。是否另做按单个 session 手动归组不在本轮默认新增范围内。

与解析同步的核心分工：解析器更新事件、项目事实、任务标题等来源数据；用户编辑更新独立的 `groups`、`group_members`，解析器不回写用户分组。查询通过稳定项目 ID 关联二者，新增消耗自然进入项目所在分组，无需因改组重解析或批量改写历史事件。

本地先改、云端再同步的最小候选流程：本地持久保存分组修改及待同步操作（携带操作 ID 和分组基准版本），立即显示组名／成员变更；云端在事务中幂等应用操作、推进分组版本并返回确认；其他访问端沿原有同步规则获取分组变化。解析事实版本与用户分组版本分别记录，统计缓存同时携带二者，避免把旧分组下的结果当作新分组的统计。本地待确认修改不被旧云端副本直接覆盖；同组并发修改用版本检查识别冲突，具体冲突处理仍需定稿。可使用同一同步入口承载不同类型实体，无需为此设计两套业务解析引擎。

本节记录用户方向及助手技术候选，并非产品实施批准。已向原型子代理同步“同 session 可跨项目”的正确性边界，不扩大原型到分组功能。

### 3.13 最新核心目标：不重复、不遗漏，按 Session 汇总不因路径拆分

用户强调最终目标是“不重复、不遗漏、合理统计”，并提出：若以 session 计算 Token，不同项目路径也应合并。该目标优先于任何按路径切分展示的候选；不能将路径变化当作另复制一份 session 消耗的理由。

应区分三个层次：可独立识别的消耗事件负责去重；session 汇总其实际消耗；项目和用户分组组织会话及其来源。相同 session 的多个文件、路径或设备副本必须合并增量事件，不能直接相加各副本的累计总数，也不能简单按 session ID 去重而丢掉不同轮次的新事件。

助手建议先将用户所说的合并落实为“同 session 跨路径仍是一个会话，保存历史路径关联”。例如 A 持有旧 100 Token，B 持有相同旧 100 加新增 20，合并应得到 120。多个项目被用户合并查看时，以其包含的唯一 session／事件集合计算，不能直接相加可能重叠的已有汇总。事件发生路径仍可用于追溯实际消耗来源。

“同 session 的跨路径记录合并”与“只因一个 session 跨过两个目录，就将这两个目录的所有其他 session 自动并成同一项目”不是同一个范围。后者目前没有被明确确认为通用自动归并规则；助手不建议在缺少其他依据时扩大到所有会话。最终项目分组的独占／重叠和自动归属政策仍需继续对齐，不能据本轮讨论擅自实现。

正确性验收需覆盖同事件副本、同 session 新增轮次、重传、迟到修订、跨路径／跨机器、父子与 fork 继承。当前原型只验证其中明确列出的子集，完整产品的统计正确性仍待后续验证。

### 3.14 修正原型比较边界：数据已在云端，比较当前页面结果可用时间

用户指出第一轮“首次串行上传合计耗时”是采集端上传云端，不属于其要比较的访问性能。真正的问题是：数据已经在云端后，由 CF 解析并直接返回当前页面所需结果，与浏览器下载后本地解析相比，效率和成本如何；并质疑补齐 1 万条数据耗时 20 多秒，要求考虑进一步优化。

助手确认第一轮范围存在偏差：A 虽然在 CF 解析事件，但仍要求浏览器下载全部规范明细、写入 IndexedDB 后本地查询，因此没有直接测量“CF 返回当前页结果”。第一轮上传耗时保留为原始诊断，不进入本轮访问性能主对比；全历史缓存完成时间也必须与当前页面结果可用时间分开。

第二轮仍在原型授权范围内，由同一个 Astra xhigh 子代理继续执行，独占 `experiments/parser-placement-v2/`；第一轮代码和所有结果保持原样，产品实现不改。新比较规定：

- 两边开始时采集输入已持久存在真实 CF；最终返回相同页面范围和统计口径，例如总计、日趋势、前 50 个唯一 session，并检查一次筛选／下一页。
- A 在 CF 解析／统计并返回当前页可直接展示的内容或数据，不要求浏览器先保存全部历史。云端尚未解析的首次处理与已解析结果复用分别测量，预处理耗时／CPU／存储单列。
- B 从同样的云端输入计算相同页面结果，空浏览器缓存与已有已解析缓存分别测量；所需输入量是方案代价的一部分，不强求两边下载相同数量的明细。输入仍不落浏览器永久缓存。
- 页面访问、完整历史缓存、采集上传是不同指标；不得用不同输出范围的数字计算等价加速比。结果可用时间也不冒充正式 UI 绘制时间。
- 实测优化批次／少量压缩响应、有界并发、批量 IndexedDB 读写、紧凑已解析状态、受影响范围更新、结果版本缓存和索引查询。
- 移除第一轮每个读取请求上的实验预算表写入，改以客户端总请求计数和有界服务端写入约束控制实验量，避免把测试仪表开销混进主要访问路径。
- 至少取得真实 CF + CUA Chrome 的 10k 测量；100k 根据运行内存和实验预算决定，不用本机结果冒充实云。保持独立合成资源并在完成后清理。

静态依据：第一轮 `browser-worker.mjs` 对 feed 使用逐批串行 `await`，每批写入一次事务，最终读取全部规范事件作固定查询；`worker.mjs` 每次请求先更新预算表。1 万历史补全涉及 21 个剩余批次，浏览器纯业务解析约 0.1 秒。因此存在明确的调度／I/O／查询优化机会，但新端到端时延仍须第二轮实测，不能提前给出加速倍数或最终选型结论。

### 3.15 第二轮优化补充：并发下载与增量查询结果

用户对第一轮 21 批串行请求询问是否可以使用多线程，并指出“逐批入库，最后读取全部事件再计算”可以解决。已将这两点传给正在执行第二轮的同一子代理。

- 网络等待通过有界并发请求重叠，比较串行小块、并发小块和单个／少量较大压缩响应；并发度按预算和实测选择，不认定线程／请求越多越快。
- 网络并发与 CPU 多线程分别说明。浏览器解析可在 Web Worker 中进行；当前纯解析较轻，不为增加线程数机械加入 Worker 池。若并行处理记录，按稳定事件身份分片或统一合并，仍保证重复与修订规则。
- 并发下载可以乱序完成，提交须遵守批次依赖和修订规则；同步游标不能跨过未完整应用的范围。队列和批次保持内存上限。
- 合理批量事务写入已解析结果；按受影响身份更新常用汇总、session 索引和页面缓存，避免每次更新后全表读取全部事件再查询。
- 修订撤回旧贡献再加入新贡献；session／turn 的 distinct 使用引用计数或受影响范围重算。数据、派生索引与同步版本在同一事务提交，不能靠直接相加批次汇总满足“不重复、不遗漏”。
- 首次没有派生结果且请求全局统计时仍须处理全部必要输入；后续增量和已有缓存访问应复用成果。最终报告区分已实现并实测的优化与后续建议。

子代理已确认按相同页面输出实施上述网络对照和增量索引；具体性能尚待第二轮结果，产品实现仍未开始。

### 3.16 已结束的确认：用户选择跨 Session 关联自动合并整个项目

用户要求继续讨论确认。助手询问：S1 在项目 A 开始，后来到目录 B 继续，B 原本还有 S2；是否让 S1 的全部消耗继续归 A、S2 保持归 B，整项目仍可手动合并；另一个选项是因 S1 跨 A/B 而将两个项目及其他会话全部自动合并。**用户明确选择第二项：“否：S1 跨过 A、B 后，自动合并两个项目及其中所有会话”。** 该选择替代助手的固定原项目归属推荐，详见 3.17 节。

不依赖该选择的正确性目标继续成立：

- 同一消耗事件的副本只计一次，同 session 的不同新增事件全部计入。

- fork 继承和父子会话包含值不能导致全局重复计数；必须按可证明的来源与实际新增消耗验收，当前原型未完成这些语义验证。
- 调整分组不改变全局 Token 总量；项目／组内的唯一会话数量不能由可能重叠的分项 distinct 直接相加。

### 3.17 已确认：同 Session 关联项目自动合并全部会话

正式确认的产品规则：同一个 session 关联到来源项目 A、B 时，自动将 A、B 合并为一个逻辑项目，其中所有会话都进入合并结果；不只合并这个跨路径 session 的两份记录。原始工作路径、机器信息、session 与事件身份继续保留。

这套归并按一致的等价关系传播：S1 连接 A/B、S2 连接 B/C，则 A/B/C 属于同一个逻辑项目。名称相同本身不是自动合并依据；来源工作目录记录与可信 session 身份提供关联，不能用日志文件搬家位置或上传设备替代执行来源。用户随后在 3.18 节重新提出优先按 Git 根目录识别项目；此前不使用 Git 自动归组的讨论已重新打开，不能视为不可变约束。

统计先去重实际事件，再汇总唯一 session 和逻辑项目；合并整个项目不意味着相加可能重叠的已有会话总数。来源项目没有被删除或改写，路径维度仍可用于追溯实际发生的消耗。

与用户手动合并的候选实现：分别保存解析产生的自动关联与用户操作产生的手动关联，最终逻辑项目由两类关联共同决定；用户手动修改先落本地待同步操作，再由云端幂等接收并同步其他访问端。解析器增加自动关联，不覆盖手动关联。已有来源项目 ID 保留，合并映射／别名让旧引用仍然有效，避免逐条重写 Token 事件。

只新增关联时，候选使用并查集维护连通分量，并持久保存可重建的关联事实；每次仅处理新关系及受影响项目。若解析修正撤销了旧关联，普通并查集不能直接拆分，应另定受影响分量重算与人工拆分政策，不能宣称已解决。合并后显示名、并发人工改名／拆分等细节尚未确认。

第二轮性能子代理已收到该选择；暂不扩大本轮原型到完整自动归并图，报告必须明确其合成 project_id 过滤属于来源维度，不能声称已验证本节完整产品语义。产品实现仍未获批准。

### 3.18 自动合并说明交互与 Git 根目录优先识别提议

用户新增明确交互要求：自动合并的逻辑项目名称旁显示小灰色圆圈感叹号；鼠标悬停时显示说明浮层。候选浮层内容包括自动合并原因、所含来源目录／项目，以及连接它们的会话；正文用可读标题，详细信息可展示稳定 ID。键盘聚焦同样可查看，触屏可点击查看。后两项为兼容性交互建议。本轮只记录产品设计，不实施 UI。

用户同时重新提出“为什么不按照 Git 根目录算”，并询问 Codex 如何处理无 Git 会话。本轮核对证据：

- 本机 Codex CLI 0.154.0 的 `codex exec --help` 明确支持 `--cd` 工作目录及 `--skip-git-repo-check` 非 Git 运行选项；非交互命令的默认 Git 检查不能被解释为所有 Codex 会话都必须有 Git。
- Codex App 当前项目接口分别返回 `projectId`、`path`、`isGitRepository`。本次实际列表中存在 `isGitRepository: false` 的本地与远程已保存项目，证明 App 的项目不等同于 Git 仓库。这里的 App 项目 ID 不能假定在每份原始 JSONL 中都存在。
- [App Server 官方文档](https://learn.chatgpt.com/docs/app-server) 分别描述 thread ID、`cwd` 和可更新的 Git 元数据；同一会话可在后续 turn 覆盖工作目录。
- [环境模式](https://learn.chatgpt.com/docs/environments/modes) 将 Local 定义为直接在项目目录中工作；[Git worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees) 明确 worktree 要求 Git，且非版本控制项目的定时任务直接在项目目录运行。
- 本项目当前 `server/importer.ts` 由 `session_meta.id/session_id` 识别会话，由 `session_meta.cwd` 与后续 `turn_context.cwd` 记录路径，没有执行 Git 根目录归一。只读实测从本仓库 `web` 子目录运行 `git rev-parse`，可解析到仓库根目录与共享 Git 目录。

当前建议（Git 仓库与无 Git 已保存项目的基本划分方向已在 3.23 节确认；具体身份映射与下述边界仍为设计细节）：先在采集端识别项目边界，再使用已确认的同 session 自动关联和人工合并规则：

1. Git 仓库内的不同子目录按所属仓库根归组，保留事件的实际 `cwd`。
2. 同一仓库的 linked worktree 通过其共享 Git 目录关联到同一仓库实例；单用 `--show-toplevel` 只能取得当前 worktree 根，不能完成这一步。
3. 无 Git 时，以可靠的已保存工作区根为依据；来源中拿不到工作区根时回退到原始会话工作目录。不能仅因位于同一父目录就把所有无 Git 文件夹并到一起。
4. 根目录是本机项目识别依据，不是跨设备通用 UUID。项目仍使用持久 ID，并保留仓库／路径关联证据。不同机器或独立 clone 的跨来源归并依赖可信来源映射、同 session 关联、同远程仓库或人工关系；其中同远程仓库自动合并已经在后续 3.31 节确认，人工拆分优先。
5. Git 信息由能访问原始工作区的采集端解析，缓存目录到仓库的映射，在新目录或有关元数据变化时复核。云端／浏览器继承采集结果；不对每条 Token 记录启动 Git 进程，也不拿上传机器当前同名目录推断旧事件来源。历史目录消失且无已保存证据时保留路径依据，不用今天的磁盘状态断言过去的仓库归属。

上述候选使仓库内换子目录无需触发额外项目合并。用户刚确认的“同 session 连接两个项目后合并全部会话”仍有效；是否改成只由 Git／工作区归组、替代跨项目 session 自动关系，用户尚未作出该修改。统计事件去重与项目归组保持独立，归组变化不增减全局消耗。

### 3.19 第二轮结果与 100k 实云压力测试续作

第二轮已完成，详见 [原型 v2 报告](../../experiments/parser-placement-v2/REPORT.md)。真实 Cloudflare Worker + D1 中使用 10k 去重事件（11k 来源观测），主代理重新核验 105 个页面样本与独立预期页面完全一致，并校验 v2 产物哈希。数据抵达时间：A 云端已准备且浏览器为空中位 0.362 秒，B 浏览器为空 4.270 秒；已有缓存的联网确认中位 0.369 / 0.339 秒；45 条新增与修订时为 1.743 / 0.713 秒。首次未解析 A 构建最终实现仅一个样本，为 2.340 秒。数字不含上传，不代表正式 UI 绘制或 SLA，样本范围、实际 CPU 与成本口径见原报告。

压力验收同时检查统计精确一致、构建未完成时不发布半成品，以及中断／重试后的正确恢复。容量测试不等同于多用户并发测试，100k 只是待测档位，并非预先指定的平台极限。无法取得 CF 实际内存峰值时标为未提供，不把本地 heap 或 JSON 大小冒充实际内存。

续作预算为仅使用唯一合成实验资源、最多约 400 MB 同时存量、1000 次 Worker 请求、100 万 D1 写行、每调用 10 秒 CPU 硬上限、1 USD 保守费用上限；不升级账户。上一轮 100 MB 是实验预算，本轮调整后仍需逐步计数和最终清理验证。主代理会审核原始结果与限制，不把尚未完成的续作写成通过。

### 3.20 100k 的实际含义与合成数据代表性

用户询问真实场景是否可能积累 100k 数据。此处 100k 指去重后的有效用量事件，不能解释为 10 万个会话、10 万条用户消息或 10 万 Token。当前解析器对新版记录优先以 `response_id` 识别事件，兼容旧版累计／增量用量；一轮用户交互及一个长期会话都可能产生许多有效用量事件，事件数不严格等于 API 请求次数。

主代理于 2026-09-11 09:55:14 UTC 以只读 SQLite 快照查询本机现有缓存，仅取聚合数值：17,086 个有效事件、207 个唯一会话、856 个有 turn_id 的唯一轮次，分布在 22 个有记录的 UTC 日期；最早 2026-06-21，最新 2026-09-11 09:54:43 UTC，最近导入约 09:54:46 UTC。每会话平均约 82.54 个事件，单个最多 1,918 个。事件包括 15,694 条 legacy 和 1,392 条新版 record。该结果是本机当前解析器的缓存口径，未进行全量原始日志独立审计，也不代表全体用户的使用分布。

100k 约为该快照的 5.85 倍；若仅做数学情景换算，每日 100 / 300 / 1000 个有效事件分别需要约 1000 / 334 / 100 天积累 100k。它可能是长期使用的容量档位，不能预先称为大多数用户的典型量或平台极限。

同时发现原 fixture 固定每事件相隔 1 小时：100k 会横跨约 11.4 年，且每会话固定 20 个事件。这会同时增加日期桶和会话索引规模，不贴近现有 Codex 历史。原有结果保留并标明结构压力性质；已通知 v3 子代理在预算内将主要分段验收补充为时间跨度现实的纯合成变体，明确事件、会话、日期数和分布。新旧输入不同的结果不得直接声称算法提速，不上传本机实际日志。

用户明确要求使用自己的真实数据并在其中扩展，同时询问 11.4 年跨度是否造成解析时间差异。已据此将 v3 后续主要验收从纯合成输入改为真实用量快照及扩展数据；测试范围限统计数据及必要归属元数据，实验接口使用临时鉴权，真实输入保存在忽略提交的本地私有目录。没有将此授权扩大到聊天／工具正文、凭据或整个本机数据库上传。

此输入来自现有解析器的 `effective_events`：旧版累计值已经转换成增量，首次来源去重已经完成，性能适配器再包装为原型支持的记录结构。不能把这轮结果声称为重新解析完整真实 JSONL 或旧版累计格式的实云耗时；真实事件身份重编号 `r-N` 也是原型分片适配，并非原始 response ID。

主代理另做固定 100k 的本地日期对照：仅改变同一份真实扩展记录的时间戳，保留排序／相同时间戳关系、所有其他字段和完全相同的 JSON 字节数。127 个有记录日拉长到 3,809 日后，5 轮中位数 JSON 解析为 169.741 / 169.869 ms、归一与去重为 509.243 / 518.449 ms、汇总索引为 529.859 / 537.456 ms、三个页面为 17.234 / 17.248 ms、索引序列化为 20.418 / 23.881 ms；各阶段总计为 1,247.149 / 1,266.400 ms（约增加 1.54%），索引体积由 5,751,022 增至 6,619,113 字节（约增加 15.09%）。

这只是本地 Node 的分阶段控制实验，若干阶段范围重叠，尚不含 CF／D1／网络和浏览器；不能单凭日期跨度把此前秒级差距或 OOM 归因于日期桶。该结果及完整样本保存在 [日期基数结果](../../experiments/parser-placement-realinput/date-cardinality-results.json)。真实输入的实云分段、页面、增量和恢复测试仍由原子代理继续，完成前不记为通过。

### 3.22 上传慢的阶段诊断：已有实测与当前协议静态限制

用户询问云端上传慢是否来自采集器。已将本地采集／整理、压缩、上行请求、云端持久接收和后续解析分开检查，不把整个原型准备时长称为采集器上传速度。

真实衍生 100k 的 v3 seed 上传共有 200 个成功请求、全部可匹配 CF invocation，采用 3 路并发、未压缩 JSON 请求体，总输入 70,504,634 字节，10:12:54.194 至 10:14:27.918 UTC 用时 93.725 秒。单请求客户端耗时中位 1,347.132 ms，CF 墙钟 211 ms、CPU 5 ms，D1 SQL 执行 0.498 ms；每次有两次 D1 调用。客户端与 CF 墙钟的成对残差中位约 1,128.279 ms，包含未单独测量的传输与客户端／连接等待，不能直接认定为纯 RTT、带宽或某个地区故障。上传计时不含本机采集和随后云端统计构建。

同一份 200 个真实衍生分片在本机压缩：gzip level 1 得到 4,286,945 字节（减少 93.92%），三轮压缩中位 83.772 ms；level 6 为 3,639,494 字节、232.399 ms。未压缩是原型上行的明确可优化点，但不能按压缩比例把 93.725 秒直接换算成优化后实测。已让原子代理在核心验收完成且剩余预算允许时补最多 8–12 次有界 raw/gzip 入站校验对照，排除 D1 写入的探测必须标明范围；不再重复上传完整 100k。

另核对当前仓库产品同步实现：`shared/usage-sync.ts` 上限为每块 200 事件／256 KiB；`server/usage-sync.ts` 每次最多串行处理 4 个数据块或 commit，每个会话另需 commit，有积压时下一轮等待 1 秒，且每轮获取 config／提交 status；`server/cloud-sync.ts` 发送未压缩 JSON。按固定真实快照 17,106 事件／207 有数据会话计算，下限为 242 个数据块＋207 次 commit＝449 个数据／提交请求，至少 113 轮，轮间等待本身约 112 秒。此为持续积压条件下的静态下限，未计大小拆块、空会话、账号请求、网络和重试，不冒充现行服务实测。

现行变化发现最多每 60 秒重扫，且会读取所有会话的完整有效事件后比较哈希；变更会话仍以整份修订上传。这会增加发现延迟和重复传输量，不能把“只续读本地 JSONL”误认为已实现端到端事件增量上传。

当前判断：已有证据直接指向原型请求体未压缩、小批次请求的往返，以及现行同步协议的调度等待／整会话修订；尚无证据证明读取原始日志是这些上传阶段耗时的主要来源。候选优化仍为增量变化记录、跨会话按字节批量打包、压缩、有积压时连续且有界并发发送、云端幂等批量写入、减少额外 config／status 请求。具体原型结果与可复算脚本见 [上传诊断](../../experiments/parser-placement-realinput/upload-diagnostics.json) 和 [输入实验说明](../../experiments/parser-placement-realinput/README.md)。产品实施未获批准。

### 3.23 按 Codex Desktop 的项目与独立对话组织统计

用户要求先按直觉采用 Codex Desktop 已有组织形式：Projects 包含有 Git 和无 Git 的项目；projectless chat 是单独对话。有 Git 时按 Git 仓库划分；无 Git 时按 App 中已保存的项目及其根目录划分，沿用 App 的项目名称展示；独立对话按自身会话身份统计。这个选择确认产品组织方向，不构成实现批准。

本轮使用当前 App 接口与本地日志只读核验：

- `list_projects` 返回项目的 `projectId`、`label`、`path`、`hostId` 和 `isGitRepository`。本机已保存的 `GUC_car_workspace` 与 `GUC_car` 均为无 Git 项目，因此无 Git 不等于无项目。
- `list_threads` 中已保存项目的任务带 `projectId`；独立 Codex 对话的 `projectId` 为 null，但仍有自己的 `cwd`。因此不能仅凭存在目录就把独立对话变成一个项目，也不能把项目归属缺失一律推断为独立对话。
- 当前任务 `01a08f0a-abc2-7e33-a5e7-c3fd8a4f15e4` 的 App 任务 ID 与其原始日志首行 `session_meta.payload.id` 相同；该元数据有 `cwd`，没有提供 `project_id`。现有 `server/importer.ts` 读取 session ID 与 cwd，尚未接入 App 已保存项目归属。

据此收敛的设计：

1. **Git 项目**：按仓库归组；事件继续保留实际工作目录。linked worktree 的共享仓库识别按 3.18 节候选处理，不以每个子目录创建新项目。
2. **无 Git 的已保存项目**：采用 App 保存的项目身份与根目录，名称用于显示。实现优先保留可靠的 App 项目 ID／映射；需要本地后备身份时由采集器持久分配，并保存主机与根目录证据。两个同名项目不能仅凭名字自动合并，改显示名称也不新建统计项目。
3. **独立 Codex 对话**：按 thread/session ID 分别统计，可以放在“独立对话”入口；不为每个临时工作目录虚构项目。继续同一对话按同一稳定会话 ID 累积，新建／fork 产生的新身份按新会话处理，并保留已知关系。
4. **采集职责**：在标准数据中明确项目类型、稳定归属与证据，再让云端／浏览器继承结果。当前 Codex 工具能读到 App 项目映射，并不证明独立安装的采集器已具备同样接口；其读取渠道与历史覆盖仍需实现核验。映射缺失的历史记录保留未解析归属状态，不能直接混入已确认的独立对话。
5. **已有规则继续有效**：同一个可靠 session 连接多个已识别项目后，按 3.17 节自动合并整个逻辑项目，并保留灰色提示说明；项目划分与归并不改变事件去重后的全局消耗。

App 中还包含其他来源的聊天；上述 thread/session 对应核验针对本地 Codex 任务，不把其他聊天来源的 conversation ID 和本地 JSONL 用量默认等同。

### 3.25 首次构建 36 秒的追查与本地算法对照

用户要求查明 100k 云端首次构建为何仍为 36.476 秒。主代理与原型子代理分别只读复核两次冷构建记录，按请求 ID 匹配真实 CF trace。新 [逐请求诊断](../../experiments/parser-placement-realinput/cloud-build-diagnostics.json) 将 36,475.5 ms 拆为：CF 应用 CPU 7,465.5 ms、CF 非 CPU wall 17,050.0 ms、CF 应用外 11,960.0 ms。最后一项中，浏览器计时请求之外的启动、预算预留、间隙和交付仅 182.75 ms。D1 SQL 执行总计 637.362 ms，是嵌套指标，不能再叠加；未记录每次完整 D1 await，不能把 17.05 秒全部命名为 D1 网络等待。

原型由浏览器依次驱动 page → 20 个 step（各 5,000 事件）→ finish，共 22 个串行应用请求及 22 个逐次匹配 OPTIONS。D1 API 调用为 page 1＋step 122＋finish 12＝135；普通 step 分别读 job、input、旧 state、受影响 agg、提交 batch、再读 job。finish 三个页面依次查询且重复取全局 totals/day。这里的 API 次数与 SQL 条数不同。最终 finish 仅约 1.282 秒；响应总计仅 6.43 KB gzip、解压 19.1 ms，不能归因于下载大页面或解压。

本轮发现并本地验证的 CPU 问题是：V3 为每个事件反复排序该会话全部时间戳。主代理新增独立 [聚合对照](../../experiments/parser-placement-realinput/aggregation-sort-benchmark.mjs)，保持同一 100k 输入及 20 个分段，把它改为每批末尾每个受影响会话一次线性求最大值。两轮预热、五轮交替测量中，纯聚合中位由 3,503.337 ms 降为 630.970 ms；所有 3,331 行完整索引在 14 次运行中一致，额外三步检查覆盖最大时间撤回、项目／日期移动、空会话。详见 [结果](../../experiments/parser-placement-realinput/aggregation-sort-results.json)。这是本地 Node 函数对照，不是实云优化结果，不得直接从 36 秒扣除该差值。

优先候选为：云端受限连续推进并持久记录每段进度，减少浏览器逐段往返；在一次 D1 batch 末尾返回真实 job 状态、合批独立读取、复用／合批页面查询；使用经验证的聚合最大值更新。当前 CPU 总和约 7.5 秒不证明所有情况可以可靠压进一个 10 秒请求，仍需有界工作与恢复机制。

另有待测拓扑线索：两次应用 trace 均为 LAX，数据库最终验证 SQL 元数据为 ENAM/ORD，部署未显式配置 placement；该位置不是逐条 cold D1 请求的路由证据，不据此量化等待。可按 [Cloudflare placement](https://developers.cloudflare.com/workers/configuration/placement/) 比较计算靠近数据库的效果。本轮只分析既有云记录并运行本地对照，没有新建／部署云资源或修改 V3 与产品实现。

### 3.27 用户要求最后一轮算法与数据结构优化：同资源 A/B 已完成

用户认可 V4 后要求：“现在做最后一次优化，看看算法和数据结构上还有没有哪里值得推敲或者改进的”。V4 的 52 文件校验清单已冻结并由主线程独立复核；V5 只在新实验目录中审查与验证算法，产品整体方案的讨论边界未改变。

最终保留两项改动：

- **批次内复用精确整数和。** 每个事件的六项 token 只转换一次；各聚合项在临时 BigInt 数组中累计，在批次结束时统一转回原有十进制字符串。持久格式、null 缺失计数、会话引用数和修订时先扣旧值再加新值的规则不变。
- **单候选新事件快捷路径。** 只有一个来源时直接确定无冲突；不存在旧事件时直接记为变化，省去把完整事件序列化后与自身或 null 比较。规范化、旧修订忽略、同修订不同内容报错、多来源选择与冲突判断继续保留。

- **不保留额外长期重放档案。** D13 选择格式变化后适配采集器／解析器、重新采集和入库，替代独立长期证据档案建议。云端有效历史、人工组织和当前可靠同步需要的临时待发／待应用状态继续保存；不因重建提前清空唯一历史。R2 不再仅为长期档案被视为必要服务。
- **验证与迁移。** D14 接受真实多设备、规模及完整链路实测；D15 接受兼容窗口、升级提示与一致切换，具体技术细节由实现方案提出。正文确认第一次近期同步后可以手动点击刷新进入第二轮全量，不改变独立的采集上传流程。

### 3.34 具体实施方案已形成

用户明确要求：“形成具体方案吧”。据此新增[具体实施方案](multi-device-cloud-panel-implementation-plan-2026-09-11.md)，以批阅后需求为约束，包含 14 个主题和 M0–M7 阶段；不继续要求用户选择已经确认的产品规则或逐项指定内部参数。

本次只读核对的实现事实：新版采集器仍以可靠上传包为终点；V5 仅完整覆盖其明确用量和固定实验路径；现有云端在候选去重前筛选上传设备，额度来源也受同一筛选限制；现有 npm 声明、CLI 和后台入口排除 Linux，CI 复用规则对应 18 个平台／运行时任务。已检查本机 Codex 状态库结构，确认存在项目、根目录和 thread 项目关联字段；只输出 schema 和必要字段结构，没有读取聊天正文用于方案。

方案的具体选择：

- 复用 Node.js 服务、本机面板、登录绑定、Worker 和 D1；共享纯 TypeScript 业务内核；第一版不增加 R2、Queues、DO 或独立轻量模式。
- 采集器移植到产品并维持一条日常原始文件读取流；本机和云端分别消费提取结果，使用同一语义，保持本机不等待网络。
- 新增 v3 gzip 采集协议、不可变批次、live／backfill 调度和分段确认；普通包直接事务应用，大任务由 D1 持久任务及 Worker 定时补扫续作。
- 全局有效事件先确定、再按实际执行设备筛选；来源候选、项目自动证据、人工分区和持久设置分别保存。CHECK 门闩与域／授权版本防止并发半提交，真实 D1 故障矩阵是 M2 必过条件。
- 页面保留统一数据接口，新增 IndexedDB、近期／全量状态和固定 cut 下的 manifest；只下载缺失或变化的已解析实体。短期变化流和实体版本用于当前同步，不作为长期原始档案。
- Linux 包括 npm／CLI 平台检查、XDG 路径、守卫、浏览器启动和 systemd 用户自启动；平台 CI 从 18 项扩为 30 项，同时更新精确文件树复用要求，不复用缺少 Linux 检查的旧成功记录。
- 旧 v2 事实先导入统一层、影子核对再切换；兼容写入口至少保留 30 天且未升级设备需继续兼容，不按到期日清空历史。回退须保留 v3 新数据、删除和人工选择。

技术依据采用当前代码、冻结实验及本轮核对的官方文档。Cloudflare 技能中的参考片段不是最终事实来源；方案按官方 D1 batch、Session、类型转换和限制说明设计，不把 Session 当作固定快照或长事务。

M0 基线／契约 → M1 共享语义与采集 → M2 小而完整的实云链路 → M3 项目与管理 → M4 全部页面与缓存 → M5 Linux／CI → M6 多设备和性能 → M7 迁移交付。每阶段列出输出与证据条件；真实多物理设备、目标操作系统和浏览器验收不能由同机模拟或局部实验代替。

方案把完整链路 60 秒、日常云端可查 P90 两秒、常用页面中位一秒列为本次建议工程目标，尚未测得或承诺；历史采集／上传／构建数据仍按各自输入与边界报告。本轮没有运行新原型、产品测试、CI 或云端实验，没有改产品代码、创建资源、提交或发布。批阅原稿继续保持原摘要不变。

## 4. 标准数据结构候选方案：尚未定稿

本节保留早期结构候选。按照 3.33 节，旧修订、来源和压缩包的保留应以当前有效事实、可靠同步及迁移所必需为限，不再以独立长期重放档案为默认目标；最新范围见批阅后需求第 5、7 节。

方向是持久保存标准事件、共享语义，并分别使用适合查询与传输的物理结构，避免每个环节重新解析原始日志。

| 结构 | 候选内容／用途 |
| --- | --- |
| `source_cursors` | 文件身份、字节位置、解析上下文、解析版本，供续读 |
| `usage_events` | 稳定事件 ID、修订号、任务／轮次、UTC 时间、执行机器、项目、模型、各项 Token、质量状态 |
| `event_sources` | 上报端、原始来源与归属证据，区分上传和执行 |
| `threads` / `turns` | 标题、父子／fork／Agent 关系，元数据独立更新 |
| `change_log` | 递增变化序号、事件及操作，直接领取增量 |
| `summary_cache` | 可重建的特定范围／口径汇总和数据版本 |
| `sync_manifest` | 固定初始化基线、分块清单、已接收／应用覆盖范围 |
| 项目分组映射 | 用户合并原项目的关系，保留原项目身份 |

候选标准事件字段：

```text
event_id, revision
thread_id, turn_id, response_id
occurred_at
origin_device_id, project_id
model, effort
input_tokens, cached_input_tokens, cache_write_input_tokens
output_tokens, reasoning_output_tokens, total_tokens
quality, parser_version
```

候选设计约束：

- 事件 ID 与设备上报位置分离，修正 Token 不应产生另一份消耗。
- Token 使用精确整数，未知保持 null；时间保存 UTC，不能只保留某个时区的每日汇总。
- 当前有效事件供查询；旧修订和来源记录用于校验／恢复，避免每次查询遍历全部修订选优。
- 传输采用版本化事件批次、公共字典、变化范围、校验值及标准压缩。
- 紧凑 JSON 加 gzip 是先前提出的候选，不是用户选定的最终编码；二进制／列式等方案是否值得，需要按真实数据测量。
- 压缩包用于传输与归档；解码后进入带索引的持久存储，翻页／筛选不重复解析整个缓存。
- 首次基线、近期优先与独立增量流需要明确覆盖和版本机制，不能把先收到的近期数据误认为完整历史。
- 各项汇总必须可从事件重建；不同机器、时间和筛选下的 distinct 任务／轮次数不能直接相加。
- 本机 SQLite、云端数据表与浏览器缓存的具体引擎、索引、压实和升级机制尚未定稿。

## 5. 额度：已选在线采集端代读，控制边界待落实

已确认：

- 同一个 OpenAI 账号的同一共享额度只维护一组结果，不按设备拆成多个面板，不相加。
- 用户选择**在线采集端代读**，不选择 Cloudflare 托管 OpenAI 凭据独立读取。
- A 离线但同账号 B 仍可读时，采用 B 的有效结果；一个来源失败不覆盖其他来源的成功结果。
- 全部读取来源不可用时保留最后成功数据；访问端完全离线时读取本机已有缓存。
- 账号身份／工作空间与本项目云端登录身份分开，不凭百分比、邮箱或设备名猜测归并。

结合“云端不控制其他机器”约束，早期提出的细化事项如下。3.33 节已经确认暂停全部上报、恢复后的当前额度更新及来源不受设备筛选限制；自主读取调度等剩余细节由实现方案处理，不重复列为用户待答项：

- 建议采集端自主读取并上报额度，云端统一结果，访问端只读云端后端。
- 访问端刷新不会向其他电脑下发 `account/rateLimits/read`、补采或执行指令。
- “自动切换来源”应怎样通过采集端自主上报和云端选取实现，避免多端重复请求过多。
- 额度自动读取间隔、手动刷新含义、暂停同步时是否继续上报额度，尚未定稿。
- 迟到结果、机器时钟误差、账号切换和身份未知的具体处理规则尚未定稿。

已经查看的证据：本项目 `server/account.ts` 使用 Codex App Server 读取额度，并有携带本机登录凭据的 HTTP 回退；官方文档描述 `account/rateLimits/read` 与 `account/rateLimits/updated`。更新通知能否覆盖所需跨设备场景尚未实测，不能视为无限制的实时全局订阅。

## 6. Cloudflare 服务候选：尚未批准

此前建议：

- Workers：鉴权、接收、校验、数据查询 API。
- D1：结构化事件、来源、索引、必要汇总和同步状态。
- R2：压缩数据包、检查点，供持久保存与重建。
- Queues：大批量历史导入、重建、压实与重试；普通小增量尽量不排长队。
- Durable Objects：未列为必需项；有明确协调需求再判断。
- KV：不承担最新额度和关键同步进度。

这些是早期候选分工，最新处理方向和首版范围见 3.33 节及批阅后需求第 3、5、7 节。云端负责业务处理、浏览器同步已解析结果的方向已有原型依据；具体服务组合仍需形成实施方案。R2／队列不预设为必需，尤其不再仅为长期重放档案引入额外存储；云端不扩展成远程控制中心。

候选可靠性设计包括：区分已持久接收与已应用可查；批次幂等；处理 R2 与 D1 之间半完成状态；队列重复投递可安全重放。服务选择、存储保留、费用提醒与资源预算未定。
