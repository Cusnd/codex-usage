## 1. 产品目标、价值和边界

### 1.1 最终要得到什么

**已确认：** 使用同一个云端面板查看多台设备的 Codex 用量及相关信息，既能看整体，也能按设备看清各自贡献。采集电脑不必一直开机，云端应保留已经同步的数据。

我对产品完成状态的理解是：用户在任意访问设备上进入自己的云端空间，能沿用熟悉的总览、分析、任务、轮次和 Agent 查看方式；选择一台设备时得到它实际产生的消耗，选择多台时得到选中设备融合后的结果；项目与任务关联清楚，额度按账号统一，数据的更新时间和完整程度可以判断。

效率、准确性、低干扰和可恢复性贯穿改造。采集器、解析器、压缩协议、数据库和缓存都是服务于这一目标的手段。

### 1.2 三个层面的成功

| 层面 | 用户应该感受到什么 | 对系统的要求 |
| --- | --- | --- |
| 能用 | 不需要到每台电脑分别打开面板才能知道整体使用情况 | 多设备采集、持久同步、统一查询、设备选择贯通全部页面 |
| 可信 | 合起来不会多算，拆开不会错归；历史不因设备离线而消失 | 全局事件身份、实际执行来源、关系去重、版本与完整性说明 |
| 好用 | 首次访问及时出现可用结果，日常更新轻快，关掉页面仍能采集 | 增量处理、当前页优先、结果缓存、后台独立运行、有界补传 |

### 1.3 本轮范围建议

**已确认继续保留：** 先完成功能与数据处理，UI 样式后谈；在线优先，浏览器缓存已经解析的结果；按 OpenAI 账号筛选任务消耗暂列 TODO。

**建议第一版完整交付：** 现有核心分析能力迁移到云端、设备分别／融合查看、项目自动与人工组织、可靠同步与恢复、统一额度、必要的状态说明、旧数据迁移。

**建议暂不主动扩展：** 团队协作权限、公开分享个人统计、跨用户数据合并、远程操作采集电脑、独立离线分析引擎、多标签收藏体系。它们没有成为本次根目标的必要条件。

“本地面板改造”不自动表示立刻删除本机入口。现有基线是本机入口只查看本机、云端入口查看已同步设备；建议继续兼容，具体运行方式见第 11 节。

## 3. 按真实使用场景检验产品

### 3.1 从一台设备开始

首次绑定电脑 A 后，A 自主发现日志并上报。访问端先取得当前可用的近期结果，并能看到历史尚未补齐的状态（可以手动点击刷新，这样就全量同步）。A 继续产生用量时，只传新增或修正部分。用户关掉面板后，A 的采集仍独立运行。

电脑 A 关机后，云端继续提供已有历史，标明 A 最近一次采集／同步时间。不能因为 A 不在线就把它从历史总计中排除。

### 3.2 多设备各自工作

A 产生 100，B 产生独立的 20，C 产生独立的 50：分别查看得到 100／20／50；融合全部得到 170。设备选择应影响所有相关统计和下钻，不能首页选了 A，进入任务详情又悄悄显示 A+B+C 的数值。

### 3.3 历史复制和跨设备继续

A 产生 100；其日志复制到 B，B 在同一任务上新增 20。全局应为 120，A 为 100，B 为 20。B 是否重复上传那份 100，不应改变结果。

这里有两个独立问题：判断两份记录是否对应同一次消耗，以及确定该消耗的实际执行设备。采集端 UUID 能说明谁采集了文件，单靠它不能解决从未标记的旧历史来源。可恢复证据应保留，无法恢复的部分使用已确认的未知归属规则。

### 3.4 同仓库、不同任务

A 与 B 分别克隆同一远程仓库，分别创建 S1、S2。已确认应归为一个逻辑项目；项目融合值包含两台设备的实际消耗，设备筛选后仍能分别看各自贡献。S1、S2 继续是两个任务，不能因为项目合并而变成一个任务。

### 3.5 人工调整项目

系统自动把来源项目 A、B 合并后，用户可以拆开。刷新、补传、解析器升级或重复读取既有关系，不应立即撤销这个选择。后续其他访问端应取得相同的人工组织结果。

如果一个新增项目 C 同时连接已经被人工拆开的 A、B，不能借 C 把 A、B 间接重新合起来。这是人工优先必须覆盖的情况；C 的具体归组建议见第 6 节。

### 3.6 一个任务包含 Agent 团队

主 Agent 和子 Agent 可以分别产生事件；团队总计由明确的委派关系组织。设备融合不应把每层“含后代合计”再次相加。普通 fork 与子 Agent 保持区别，继承的旧历史不产生新的消耗。

### 3.7 同账号额度从另一台在线设备更新

A、B 使用同一 OpenAI 账号，A 暂时离线，B 仍能读取有效额度。云端继续显示这一账号的一组结果，并说明最近成功采集时间。它不能因为用户正在看 A 的用量，就被迫只使用 A 的旧额度；设备筛选与额度的具体联系见第 9 节建议。

### 3.8 网络中断和历史积压

A 离线期间继续产生本地记录。恢复网络后，待发数据从已保存位置继续上传；新增记录保持较高优先级，旧历史也持续取得进展。访问端显示的是已经可查询的数据，并说明尚未补齐的部分。

### 3.9 重装、改名和清理

设备改显示名称不应创建新的历史来源。清理统计缓存应能重建，并避免重复计数。重装丢失身份、完整复制采集状态到另一台机器、删除云端历史，则分别需要明确规则，不能都归为普通“刷新”。

### 4.1 功能迁移矩阵

| 功能 | 云端应该提供的行为 | 分别／融合时的关键要求 |
| --- | --- | --- |
| 总览 | 已同步范围的用量摘要、活动趋势、可用额度与数据状态 | Token 受设备选择影响；额度维持账号共享语义 |
| 趋势与时段比较 | 按日／小时、当前时区与同口径基准比较 | 迟到历史回填原发生时段；比较两边使用相同设备和统计规则 |
| Token 构成 | 输入、缓存读取、输出及可用的细分值 | 缓存读取不重复加到输入；缺失值有说明 |
| 项目分析 | 来源项目解析为逻辑项目，支持查看合并原因与人工调整 | 项目关系在云端空间内一致；设备选择仅改变统计范围 |

| 轮次 | 任务内和跨任务查看轮次 | 身份至少包含所属 Session；相同短 turn_id 不跨任务混并 |
| Agent 团队 | 自身、后代和团队范围可区分 | 明确关系、唯一事件集合、设备筛选贯通 |
| API 参考成本 | 按清楚的价格口径推算，显示缺失项 | 不当作账号实际账单；融合结果采用一致的价格版本 |
| 设备管理 | 绑定、命名、状态、暂停、撤销和历史操作 | 操作后历史与新数据的行为可解释 |
| 设置 | 时区、展示口径、访问端同步、采集端自主设置 | 浏览器偏好、云端共享设置、采集器设置分开 |

### 4.2 建议采用一套筛选语义

设备范围、时间范围、项目、模型、推理强度、未知项等形成明确的查询条件。列表到详情、详情到轮次、Agent 下钻和返回列表，都携带这些条件；改变范围后重置失效的分页或选中项。

建议“查看完整任务”默认扩大时间／模型等任务内筛选，但保留设备范围；若要看该任务的全部设备，应有明确动作。现有导航代码保留设备参数，可作为迁移基础，见 [navigation](../../web/navigation.ts)。这里的具体详情展示可以由你修改，但不能让同一个数字在没有说明的情况下更换范围。

### 4.3 建议提供三种可辨识结果

- **按单设备查看：** 仅该设备实际产生、且符合其他筛选的消耗。
- **选中多设备融合：** 选中设备的事件集合去重后统计。
- **按设备比较：** 在相同时间和口径下列出各设备贡献；是否做成专门对比页可后续决定，第一版已有分组／表格即可。

融合视图仍可展示设备贡献明细，不要求切换到另一套数据或重新解析历史。各设备贡献可相加的前提是执行归属互斥且未知部分单列；任务数等 distinct 指标不满足简单相加，见下一节。

## 5. 分别与融合统计的统一口径

### 5.1 先形成全局有效事件，再按实际执行设备筛选

**建议的统一计算顺序：**

```text
当前云端空间内的来源证据
  → 识别同一消耗、处理版本和重复，形成有效事件
  → 确定／标记实际执行设备、任务、轮次、项目来源
  → 应用设备、时间、项目、模型等筛选
  → 汇总、排序、分页和返回
```

不能先只取“由设备 A 上传的记录”来代替“A 实际产生的记录”。例如 A 产生的历史由 B 补传，选 A 时仍应能看到；选 B 时也不能把 A 的历史算作 B 的贡献。

当前 [云端查询](../../cloud/src/usage-query.ts)在候选选优之前按上传设备筛选，这与新增的实际执行来源要求存在需要改造的边界。这里是对现有代码与目标规则的比较，不是已对你的历史发现错账的断言。

### 5.2 数值示例

设 A 的实际事件合计 100，B 新增 20，C 独立新增 50；B 还持有 A 的那份 100。另有 5 的旧历史无法确认执行设备。

| 视图 | 应显示的 Token | 说明 |
| --- | ---: | --- |
| A | 100 | 不受该记录由 A 还是 B 补传影响 |
| B | 20 | 排除 A 的历史副本 |
| A+B | 120 | 去重后的选中设备消耗 |
| C | 50 | 独立事件 |
| 来源未知 | 5 | 保留用量，设备归属未确认 |
| 全部 | 175 | 100+20+50+5，未知不能悄悄丢失 |

建议“全部设备”包含来源未知，并单列其贡献；用户明确选 A 或 B 时不把未知量强行分配进去。人工归属把这 5 从未知桶移到所选设备，全局仍是 175。

### 5.3 不同指标的合并方式

| 指标 | 规则 |
| --- | --- |
| Token 数值 | 对唯一有效事件求和；修订用新值替换旧贡献 |
| 事件数 | 唯一有效消耗事件数；不等同原始日志行数，也不保证等于 API 请求次数 |
| 任务数 | 对当前事件集合涉及的 Session 去重；跨设备同任务不能各算一次后相加 |
| 轮次数 | 按 Session 与轮次身份联合去重 |
| 项目数 | 按当前逻辑项目映射和筛选范围确定；人工拆分可能改变项目数但不改变 Token |
| 缓存比例 | 用同一有效范围的分子和分母重新计算，不平均设备百分比 |
| 最早／最近活动 | 使用实际事件时间；新的上传时间不把旧任务变成今天的新消耗 |
| Agent 团队 | 唯一自身事件与明确后代事件集合的合计，不叠加每层含后代总数 |
| 参考成本 | 使用统一价格与缺失规则计算，不能混加不同设备自定义价格下的预计算值 |

### 5.4 精度、缺失和修订

Token 整数端到端保留精度；当前契约已使用十进制字符串表示可空整数。`null` 表示缺失，不转换成 0。已知部分可以计算时，建议同时显示缺失事件数量／完整性；无法形成可靠值时保持未知。

缓存读取已经包含在输入中，不能再次加到总输入；推理输出是否包含在某字段中按原始记录语义处理，不能把细分字段都相加当总量。保持原解析规则的独立对照，避免只比较最终总数而漏掉组成错误。

事件从 10 修正为 12，最终贡献为 12。修订涉及时间、设备、项目或模型时，旧桶扣除、对应新桶加入；全局与各视图同时更新。处理结果应说明修订，而不是伪装成新增一条独立消耗。

### 5.5 时间、成本与口径版本

建议事件保存原始 UTC 时间，查询显式携带时区和固定时间边界；相同查询的一组卡片使用同一个边界。迟到数据可以更新过去的日期桶。设备墙钟误差需要记录质量，不用上传时间直接替换实际发生时间。

参考成本的变化不改写 Token 事实。价格表版本、统计规则版本、项目映射版本变化，都可能使旧缓存失效。若不同浏览器选择不同时区或成本设置，结果可以不同，但必须能从明确的查询口径解释。

### 6.1 先统一几个容易混用的词

| 概念 | 建议含义 | 不随什么改变 |

| 逻辑项目 | 云端按自动关联和人工选择组织的一组来源项目 | 访问端当前只筛选哪台设备 |
| Session／任务 | Codex 会话身份，串联其事件和轮次 | 标题修改、文件副本、访问入口 |

### 6.2 采集端识别来源项目

**已确认方向：** Git 项目按仓库识别；无 Git 的已保存项目沿用 App 项目；独立对话按自身 Session 组织。

建议的识别顺序与边界：

1. 能识别 Git 仓库时，保留仓库根、实际工作目录及共享仓库线索。子目录不产生额外逻辑项目；linked worktree 根据共享 Git 目录关联本机同一仓库实例。
2. 无 Git 时，使用可靠的 App 项目映射与根目录，沿用其显示名称；App 项目 ID 保留来源主机上下文，不假设它天然是全球项目 ID。
3. 已明确属于 projectless chat 的记录，作为独立对话，不为其临时目录创建虚构项目。
4. 只有 cwd、但拿不到项目映射的历史，保留“项目归属待识别”。没有映射不等于已证明是独立对话。
5. 项目证据尽量随采集记录保留。现在的文件系统与 Git 配置不能无条件证明过去的项目边界；路径消失也不能导致历史消耗消失。

**待验证：** 原型可以接收显式的已保存项目映射，但尚未自动接入独立安装环境中的 App 项目数据来源。当前任务工具能列出项目，不等于发布后的采集器有同样能力。

### 6.3 自动归并规则

以下两类依据已经确认，均需要保留合并原因：

- 同一个可信 Session 连接来源项目 A、B，合并 A、B 及其中全部会话；连接继续传播。
- 不同设备的独立克隆，可以确认同一远程仓库时，合并为同一个逻辑项目，不要求共享 Session。

项目名相同、目录末级相同、任务标题相同，都不能独立成为归并依据。项目归并只改变组织，不替代事件去重；两个独立 Session 不因同仓库而被合成一个 Session。

### 6.4 “同一个远程仓库”需要怎样确认

**建议：** 为远程仓库建立规范身份，至少保留主机与仓库路径／可靠仓库标识，以及归并依据。确定等价的 SSH、HTTPS 地址可以映射为同一身份；不同服务实例、不同 owner 或不同仓库不能仅凭名字合并。

建议默认使用项目实际主要仓库的远程配置作为证据，避免把“任何 remote 相同”都当作同仓库：一个 fork 项目可能保留指向上游的 remote，它不因此等同于上游项目。多个 remote、镜像地址、仓库迁移／改名、私有 Git 服务的地址规则，需设计明确的候选选择和人工纠正入口。

远程配置可能包含用户信息或令牌。采集端应生成去除凭据的仓库身份／显示地址，不把整份 Git 配置或含凭据 URL 上传。此项只涉及识别项目所需的元数据。

**待验证：** 地址规范化与“同仓库”判定须有真实与合成样例；不能用粗暴删除所有大小写、端口、后缀等方式制造错误等价。无需为了识别仓库默认申请仓库读写权限。

### 6.5 人工拆分是持久的组织选择

**已确认：** 用户可以覆盖自动合并，后续同步保留人工拆分。

建议把人工选择表示为对来源项目的持久划分／约束，并与自动关联证据分别保存。自动证据仍可说明“为什么原先建议合并”，但不能覆盖用户划分。

只删除 A—B 一条合并边不够：若 A—C—B 仍连通，下一轮会再次合并。因此，人工拆分的有效性应对最终组织结果检查，覆盖间接连接。技术上只重算受影响的部分，但一个受影响部分很大时仍需分段和一致发布，不能承诺永远常数时间。

**建议的延伸行为，尚未确认：** 若新来源项目 C 同时连接用户已经拆开的两组，C 暂不自动把它们连起来，也不随到达顺序随机加入某一组；保留 C 及关联说明，允许用户选择归属。全局 Token 继续完整统计，只有项目组织待确认。

若用户主动执行新的合并，应明确它是否取代原拆分约束。建议在操作中显示将受影响的来源项目，并将人工选择作为一个完整修改发布，而不是逐条更新到一半就显示新总数。

### 6.6 名称与选择范围

**建议：** 用户指定的逻辑项目名称优先；否则按稳定的来源名称规则生成显示名，不随最后上传设备来回变化。设备与路径作为来源明细保留。

项目的逻辑身份在云端空间内统一。只看设备 A 时，项目仍是同一个逻辑项目，但只统计 A 在该项目内的消耗；取消设备筛选后恢复全部贡献。筛选不应重新运行一套不同的项目归并规则。

自动合并提示应能说明依据是共享 Session、同远程仓库还是两者兼有，并列出来源项目。已有灰色感叹号的要求保留，样式与交互细节后续处理。

## 7. 身份体系：每个标识只回答一个问题

### 7.1 身份分层

| 身份 | 回答的问题 | 关键边界 |
| --- | --- | --- |
| 云端空间／用户 | 数据属于谁的面板 | 不等于 OpenAI 账号，也不等于设备 |
| 设备身份 | 这是哪台被管理的采集设备 | 显示名可改，历史身份不能随名称变化 |
| 采集实例 UUID | 谁读取并上报了这批数据 | 不自动证明所有被读取的旧记录都在该机器执行 |
| 来源 ID + 代次 + 位置 | 哪个版本的哪个来源位置提供了证据 | 可定位和重放；不是跨设备消耗身份的替代品 |
| 事件身份 | 是否为同一次实际消耗 | 不应由上传批次、当前文件名或随机重建决定 |
| Session／轮次身份 | 事件属于哪个任务与轮次 | 任务标题不是身份；轮次需所属任务上下文 |
| 来源项目／逻辑项目身份 | 原始工作区与最终组织分别是什么 | 本地路径不能单独充当跨设备通用 ID |
| OpenAI 账号身份 | 哪些额度报告属于同一账号与对应额度范围 | 不按邮箱展示名、百分比或设备名猜测 |
| 批次／修改操作 ID | 这是不是同一次传输或编辑的重试 | 重试复用；不当作一条新的消耗 |

具体字段名、UUID 形式和存储位置属于实现设计。重要的是这些含义不能相互代替。

### 7.2 来源副本与实际消耗

一条有效消耗可能有多个来源证据。云端需要知道哪些证据支持该事件，哪个字段来自哪里，以及是否存在冲突；正常查询可以读取已经形成的有效结果，不必每次重新遍历所有副本。

有可靠全局 response 身份时，可作为事件身份依据之一。没有该身份的旧版累计记录，仍需处理累计差分、重复报告、显式记录替代、fork 继承与跨来源匹配。用“来源位置”标识观察记录只能避免同一来源重复导入，不能自动解决不同文件里的同一消耗。

不能仅因为两个事件时间相近、Token 相同、标题相同就删除其中一个。不能因为一个来源先到就永久拒绝之后的真实补充。来源修订序号只能在它自己的来源内比较；不同设备的序号或墙钟没有天然的真伪优先级。

### 7.3 正常归属与特殊旧历史

正常在 A 产生并由 A 采集的记录，应保留 A 的执行来源。已经带来源的记录被转发后继续保留，不改为最后上传设备。只在证据确实不足时进入未知归属，并说明人工指定与原生证据的区别。

**待验证：** 新采集器原型目前可以按配置声明本地原生／保留导入来源，但没有自动识别一个混合文件中哪些旧事件来自 A、哪些新增来自 B。产品接入需要补足这一边界或明确输入契约，不能用生成 UUID 宣称全部解决。

### 7.4 重装与复制采集状态

**建议：** 普通升级、进程重启、重建可再生统计库保留采集身份；原始数据处理游标与不可再生身份分别保存。换设备时创建新的采集实例，已有事件的原始来源保留。

完整复制整套采集状态会同时复制 UUID，系统不能靠 UUID 自己知道这是克隆还是恢复。建议提供显式的“恢复原设备”与“作为新设备接入”语义，并在同时活跃的同身份写入发生冲突时停止不安全覆盖、给出可处理状态。

**待决定：** 第一版是否提供界面化的设备接续／更换流程，还是先提供明确的管理命令与说明。正常绑定新设备沿用已有流程，不要求用户理解内部标识。

### 8.2 采集器与业务解析器的职责

**建议：** 采集器读取完整日志行、提取必要用量证据与上下文、附来源信息、识别本机项目证据、持久保存游标并压缩组包。它理解输入格式，但不承担云端全局去重与全局汇总。

云端业务解析负责把旧版累计／新版明确用量等证据解释为有效消耗，处理多来源、修订、关系、归属和派生统计。浏览器使用已解析结果完成页面查询交互和缓存，不再维护另一套原始用量解释规则。

这种分工需要共享明确的语义契约，尤其是采集器不能为了减少体积丢掉业务解析必需的旧累计值或上下文。原型已经保留这些字段，但完整云端接入仍未完成。

### 8.3 首次接入与两次访问端同步

| 过程 | 应做什么 | 不应混淆什么 |
| --- | --- | --- |
| 新设备接入 | 采集近期／活跃来源优先，后台持续形成全部可采历史 | 不等待浏览器第二次点击才上传旧历史 |
| 访问端第一次触发 | 取得当前页面与近期、活跃范围的已解析结果 | 近期完成不表示全部历史完整 |
| 访问端第二次触发 | 补齐云端可提供的全部已解析历史覆盖，复用第一轮数据 | 全量不等于重下重算相同版本 |
| 初始化之后 | 日常只同步新增、修订、关系和设置变化 | 手动刷新不应变成每次重建历史 |

**建议细化：** 只有一轮成功形成其约定覆盖才推进初始化阶段；失败保持可恢复进度。执行中再次触发可登记下一轮意图，不并发启动相同范围的重复任务。用户没触发第二轮时，采集端仍继续上传，当前页仍可查询云端已经有的数据。

若第二轮时部分采集设备本身尚未上传完整历史，只能声明“已缓存云端当前可提供的范围”，同时保留各设备仍在补齐的状态。访问端之后持续吸收补来的历史，不需要重新开始初始化。

### 8.4 日常新增、历史补传和无变化

新增数据触发来源续读，持久形成待发变化；上传跨会话组包，少量记录不为了攒满包长期等待。有积压时持续发送，并限制内存、并发和服务端事务规模。

历史补传采用有界轮转，给新事件保留处理机会，同时保证旧历史最终取得进展。热点任务不能永久垄断采集与上传。无变化时只做必要的轻量检查，不重新读取所有有效事件再比较整会话哈希。

### 8.5 可靠确认与版本发布

建议明确以下状态：本机已持久待发、云端已持久接收、云端已应用并可查询、访问端已取得／缓存。一个“已同步”状态不足以表达全部阶段。

普通小批次可以在一次请求内完成接收和应用；大导入可分段，但必须有持久待处理记录和能够独立恢复的执行机制。完成响应丢失后，重发同一个不可变批次得到同一确认，不能新增一份消耗。

事件、项目关系及相关统计按一致版本发布。大重建期间继续提供上一份完整结果，并显示更新中；首次无旧版本时显示尚在准备。不能让首页已经是新版本，项目页仍引用未更新的旧索引却都标成同一时刻。

### 8.6 多台设备同时上传

接收可以并行，修改同一有效事件、项目关系或汇总时必须有一致的并发保护。单来源修订、上传批次顺序、云端结果版本各司其职，不能混用一个全局时间戳。

建议第一版优先采用易验证的云端数据域版本保护／协调方式；若冲突则重新读取受影响状态并计算，不让两个上传者同时在同一个旧总量上各自覆盖。具体用数据库事务与版本检查还是协调服务，应由真实竞争测试决定。

## 9. 账号额度与官方历史

### 9.1 账号与设备是两个维度

**已确认：** 同一 OpenAI 账号共享一组额度，在线采集端代读并上报。一个账号可以由多台设备提供读取结果；一台设备也可能在不同时间登录不同账号。

账号额度、官方每日历史、从设备日志计算的 Token 是不同数据来源。它们不要求数值相等，也不能用设备 Token 去反推一个必然正确的剩余额度。

### 9.2 建议额度不随用量设备筛选切换读取来源

例如正在查看 A 的 Token，但 A 离线、同账号 B 有更新的有效额度。建议额度仍显示该账号的共享结果，采集来源 B 作为辅助信息，而不是退回 A 的旧结果或重复生成一张卡片。

**待决定：** 设备筛选是否完全不影响显示哪些账号，还是只缩小相关账号列表。无论选择哪种，选定同一账号后，云端取有效结果时不应仅局限于当前用量筛选的上传设备。

### 9.3 自主读取和刷新含义

采集端按自己的额度调度读取，成功后上报。访问端刷新仅读取云端已有结果，不发命令要求另一台电脑立即读取 OpenAI。

**建议首版沿用适用的现有间隔与设置，先保证语义正确。** 不为了去掉少量重复请求就立即增加“选举唯一读取设备”的复杂机制；先记录多设备请求量，只有重复读取形成实际负担时再设计协调。任何协调仍应服从采集端自主与访问端不远控的边界。

采集额度、上传额度、刷新页面是三个动作。暂停云端同步时是否继续在本地采集额度、是否同时暂停用量和额度上报，需要明确定义，见第 11 节。

### 9.4 新鲜度和失败处理

建议保留账号身份、额度范围／窗口、读取结果、原始采集时间、云端接收时间、来源与失败状态。一个来源读取失败不能清空另一个来源的成功结果。

不能只按“最后收到”推断一定最新：离线旧报告可能晚到。也不能只信设备墙钟。若来源提供可靠版本／时间证据，应使用；否则需要约束迟到报告、保留冲突信息，并以之后成功的新读取更新。

全部来源暂时不可用时保留最后成功值和时间。重置时间经过后，可以提示等待新读取确认，不能自行保证剩余已经是 100%。页面完全离线时只能说明当前缓存的时点，不能称为实时额度。

### 9.5 账号切换和官方每日历史

设备从账号 X 切换到 Y 后，新的报告属于 Y，不能把 X 的历史标签改成 Y。身份无法确认时不猜测合并；原成功数据保留其账号归属。

官方每日历史保留来源日期与口径，不强行套入设备日志的时区重算，也不因同一账号在多台设备重复提供而相加。是否长期显示已不再登录但有历史的账号，建议允许查看并明确当前是否仍有读取来源。

## 10. 数据完整性、状态与错误表达

### 10.1 完整性至少分三个层面

| 层面 | 需要回答的问题 | 可能出现的状态 |
| --- | --- | --- |
| 单设备来源 | 这台设备当前可发现的历史采到了多少 | 首次发现中、近期已采、历史补齐、遇到待处理来源 |
| 云端应用 | 已接收数据中多少已进入可查询结果 | 等待、已接收待处理、应用中、已发布、失败待恢复 |
| 访问端缓存 | 当前浏览器有哪些范围与版本 | 当前页可用、近期覆盖、全历史覆盖、存在缺口／需更新 |

只给出最早和最晚日期不能证明中间没有缺口。建议对初始化保存可核对的来源／分块清单与连续进度，并同时保留动态新增的来源状态。

“历史完整”应限定为已接入设备及其可获取资料的覆盖，不能保证包含用户从未上传、已经删除或其他未接入设备上的所有历史。

### 10.2 状态应该帮助用户做判断

建议每台设备可看到：最近活动证据、最近采集、最近接收、是否有待发／待处理、历史覆盖阶段、最近错误。没有新用量不能直接等于离线；有心跳但某个来源失败也不能等于历史完整。

页面优先显示可用结果，同时明确范围。发现某台设备积压时，不阻止其他设备显示；整体值标为已知已同步范围。未知与尚未收到的数据不能以 0 代替。

### 10.3 错误分类与恢复建议

| 情况 | 建议行为 |
| --- | --- |
| 普通断网／超时 | 保存待发进度，退避重试；已有历史继续可读 |
| 确认丢失 | 重发同一批次／查询已有确认，不重造事件 |
| 设备被撤销 | 停止该绑定的数据上传，保留本地记录及已有云端历史 |
| 暂不兼容的协议／字段 | 明确需要升级或修复，不悄悄丢字段继续报完整 |
| 无法解析的完整记录 | 记录来源位置与问题；可继续处理安全范围，但覆盖状态必须反映问题 |
| 半行尚未写完 | 等待补齐，不把半条 JSON 当永久坏数据或推进完整游标 |
| 云端容量／限流 | 背压与可解释状态，本机保留必要待发数据 |
| 浏览器缓存不可写 | 在线查询仍可用，明确持久缓存未完成 |
| 项目归属不明 | 保留事件与全局统计，单列待识别项目归属 |
| 人工修改冲突 | 保留双方意图，按最终选定的产品规则处理 |

## 11. 设备管理、本地入口与生命周期

### 11.1 接入与退出

**现有基线：** 用户在采集端启动绑定，在云端登录并核对设备名称后加入自己的空间；每台新设备追加进入，不替换已有设备。网页登录身份与 OpenAI 账号身份分开。

建议继续保留清楚的设备列表和名称编辑。名称方便识别，不能用它推断设备身份；同名设备可以并存，并通过更具体的来源信息区分。

退出网页只结束当前访问会话，不停止已授权采集端。卸载采集器、停止后台进程、暂停上传、撤销云端接收权限、删除历史，分别影响不同状态。

### 11.2 建议把管理动作的含义写清楚

| 动作 | 本机行为 | 云端与历史行为 |
| --- | --- | --- |
| 关闭网页 | 后台继续按配置采集与上传 | 其他访问端照常使用 |
| 本机停止服务 | 停止该服务的采集与上传 | 已有云端历史保留 |
| 本机暂停上传 | 建议继续采集并保存必要待发数据 | 该设备的新变化暂未到达云端 |
| 云端暂停某设备接收 | 云端不接收该绑定的新数据；采集端在正常协议交互时获知状态 | 保留历史；不等于云端启动／停止另一台机器上的进程 |
| 恢复同步 | 从已保存进度继续，复核绑定与来源状态 | 不重置历史总量，不把重放当新增 |
| 撤销设备 | 后续上传鉴权失效 | 默认历史保留，设备标为已撤销 |
| 改显示名 | 不改采集 UUID 与历史事件归属 | 所有访问端取得新名称 |
| 删除历史 | 本机原始日志按原边界保留 | 具体删除范围必须明确，见下一节 |

**待决定：** “暂停上传”是否同时暂停用量与额度上报。建议默认暂停该设备全部云端上报，本地采集按本地设置继续；恢复时用量补传，当前额度优先提供重新取得的有效值，避免把很久前的报告当当前状态。

### 11.3 删除历史存在两种不同语义

当前文档与管理代码的基线是移除某个上传设备的云端副本，其他设备副本仍可见。引入实际执行设备后，“删除 A 的历史”可能被用户理解为删除 A 真正产生的全部消耗，即使那些记录由 B 上传。

| 删除语义 | 例子 | 结果 |
| --- | --- | --- |
| 移除 A 上传的来源副本 | A、B 都保存同一个事件，删除 A 的副本 | B 的证据仍支持该事件，融合统计可能不减少 |
| 删除归属于 A 的实际用量 | A 的事件由 A、B 各上传一份 | 同一云端空间内该实际事件应被删除／排除，不能被 B 的副本重新恢复 |

**建议第一版保留现有删除副本能力，但使用准确的名称与说明；是否新增按实际消耗删除，需要明确决定。** 两个动作不能共用模糊的按钮描述。

如果采用实际用量删除，需要云端删除标记及重放规则，并同时处理事件别名、旧批次和新绑定再次上报的副本。删除标记不能在旧数据仍可能合法重放时过早丢弃。删除是用户主动操作，正常原始文件消失／归档／设备离线不自动触发同样行为。

### 11.4 本地模式如何保留

**现有基线：** 本机入口查看本机，云端入口默认融合已同步设备。建议第一版继续兼容既有本机使用习惯，不把本机页面无说明地变成全设备结果。

建议区分运行需求：

- 需要本机面板时，保留本机查询所需的业务处理；尽量复用同一语义代码和已提取证据，避免两套规则分叉。
- 只需要向云端提供数据的设备，可以考虑提供轻量采集模式，省去不使用的本机完整分析；是否作为第一版功能待决定。
- 云端浏览器查询不依赖本机页面是否打开，也不绕过云端向采集端取数据。

本机与云端可以复用业务语义，但它们持有的数据范围不同：本机可能尚未收到其他设备的归并事实。若继续支持本机项目编辑，应说明它是本机设置还是同步到云端的用户组织，不能悄悄混用两个范围。

### 11.5 安装、升级与兼容范围

当前实验主要在本机 Windows／Chrome 完成。产品需要按实际支持的操作系统和浏览器复验，特别是文件监听、路径大小写、Git worktree、休眠恢复、后台启动和缓存持久化。

建议发布前定义：支持哪些采集平台与 Node 版本，哪些访问浏览器参与验收，旧采集协议如何提示升级。沿用现有已支持范围作为起点，不把一次 Windows 实验外推为其他平台都通过。

## 12. 浏览器缓存、查询与设置归属

### 12.1 缓存的角色

**已确认：** 在线使用优先，浏览器缓存已解析结果。缓存用于快速再次显示、减少重复请求及读取已有历史，不要求保存原始待解析日志。

建议先显示可用的已缓存结果并标明时间，再按用户同步设置确认版本。查询失败时保持最近成功内容与失败说明，不把旧数据显示成“刚更新”。缓存不可用时，在线查询仍应能工作。

当前页可用与全部已解析历史缓存完成是两个进度。前者不能被后者拖住，后者也不能被一次首页响应误报为完成。

### 12.2 一个缓存结果需要关联什么

建议缓存键和响应元信息包含：云端空间、查询范围、结果数据版本、统计规则版本、项目组织版本、时区及必要的成本设置版本。分页要么固定结果版本，要么在变化时明确重置，避免翻页途中重复／漏项。

只同步设备 A 的增量时，可以只使受影响范围失效；但它可能改变 A+B 的合计、逻辑项目或跨设备任务，因此不能只刷新 A 的单独页面。

新增迟到历史影响过去日期，项目拆分影响组织维度，价格设置影响参考成本。它们都不需要重新解释所有原始日志，但需要让相关结果与缓存更新。

### 12.3 全历史覆盖与缓存容量

建议把已有的两轮加载规则落实为持久范围／版本清单，断点继续，避免每次打开都重新下载全部历史。

**待决定：** 浏览器空间不足时，是停止后台全历史补齐并提示，还是允许淘汰部分已解析明细。我的建议是优先保留设置、当前页与近期结果，明确全历史缓存未完成；不能一边自动淘汰、一边仍称“全量已缓存”。这不会影响云端已保存的历史。

退出账号、切换云端空间或用户主动清缓存时，需要隔离和清理对应访问状态。缓存的存在不应让另一个登录用户看到前一用户的统计与项目名称。

### 12.4 设置应该存在哪里

| 设置类型 | 建议归属 | 原因 |
| --- | --- | --- |
| 来源目录、后台运行、采集与额度读取间隔 | 采集设备本地 | 这些控制本机工作；访问端不远程调度 |
| 逻辑项目合并／拆分、人工来源归属、设备名称 | 云端空间共享，访问端可有待同步操作 | 多端应看到同一组织和来源解释 |
| 时区与参考成本配置 | 建议有云端默认值，查询明确携带实际值 | 统一默认口径，同时让差异可解释 |
| 页面筛选、分页、当前展开项 | 浏览器／地址栏 | 属于当前查看上下文，避免另一端操作打断当前阅读 |
| 自动同步间隔 | 建议作为访问端偏好，沿用原有控制方式 | 不同访问设备可有不同使用节奏；不控制采集器 |
| 纯展示选项 | 沿用现有设置并明确本地或共享 | 不应导致原始统计重解析 |

这一分层是建议；你可以指定哪些偏好应跨访问端同步。项目组织与页面临时筛选不宜使用同一套“最后保存覆盖一切”的设置对象。

## 13. 云端存储与处理方案的思考

### 13.1 三类数据应分别保存

| 数据层 | 内容 | 是否可直接丢弃后重建 |
| --- | --- | --- |
| 必要来源证据 | 经白名单提取的用量记录、上下文、来源和修订证据 | 取决于是否还有可靠重放来源；不能假设采集电脑永远在线 |
| 有效事实与用户操作 | 规范事件、来源归属、任务关系、人工项目选择 | 人工操作不能靠重读日志恢复；有效事实可由充足证据重建 |
| 派生索引与结果 | 汇总、趋势桶、排序索引、页面缓存 | 应可重建，但重建期间保留可用版本 |

只保存页面汇总，未来无法修复去重或详细查询；保存所有原始聊天日志又超出本项目需要。建议持久保留足以复算的必要证据与用户操作，具体压缩、版本和保留周期待方案定稿。

### 13.2 初始服务组合建议

沿已有实验和调研，第一版可以以 Workers + D1 的接收、事务状态、规范数据与查询为基础。R2 用于确实需要的压缩重放档案／大规模不可变块；Queues 用于必须脱离访问请求继续执行的持久后台任务；协调服务仅在并发设计需要时引入。

这不是最终服务选型，也不以“100k”这个数字单独要求增加所有服务。选择依据是实际工作集、事务范围、写入竞争、独立恢复需求与维护成本，而不是服务数量。

若大导入必须在访问请求结束后继续，持久待处理记录只是必要条件，还必须明确谁会再次领取并执行。不能把请求结束前碰巧做完或短暂后台回调当作完整的任务恢复机制。

### 13.3 可查询结构而非一个越来越大的 JSON

建议保留按事件／来源／任务分片或索引的持久结构，以及常用聚合。新增 10 条通常只读取受影响的规范状态与少量汇总，而不是把全部历史反序列化后重新保存。

但是，任意设备子集、任意时间范围、项目、模型和 Agent 团队会形成大量查询组合。不能为每个设备子集都预计算一份结果；也不能假设每个查询都能由简单单设备汇总相加。

建议：常用可加和指标可使用设备／时间等基础桶，任务与轮次 distinct 使用可验证的成员／引用或范围查询；较复杂组合通过有索引的事实查询完成。缓存实际被请求的结果，并明确缓存版本。用真实查询分布测性能，不只优化固定首页。

### 13.4 概念数据契约

以下是职责示意，不是已经定稿的字段或表结构：

| 实体 | 必要信息 |
| --- | --- |
| 采集批次 | 协议版本、采集身份、来源代次和覆盖、批次 ID、摘要、必要记录 |
| 来源观察 | 稳定来源位置、来源修订、原始用量证据、上下文、归属证据 |
| 有效事件 | 事件身份、当前版本、Session／轮次、发生时间、执行来源、项目来源、Token、质量 |
| 任务元数据 | 稳定任务 ID、标题及依据、父子／fork 关系、来源与版本 |
| 项目关系 | 来源项目、远程身份与证据、自动关系、人工划分与修改版本 |
| 同步确认 | 已持久接收、已应用范围、批次回执、结果版本与缺口 |
| 查询结果 | 数据、完整筛选口径、版本、覆盖／未知说明、分页信息 |
| 账号报告 | 账号引用、额度范围／窗口、成功值、采集与接收时间、来源及状态 |

### 13.5 原子性与可修复性

建议把游标推进与对应待发数据持久化放在同一提交边界；云端把事件变化、相关索引、同步回执与发布版本放在可验证的一致边界。多个服务之间不假设存在一次天然的跨服务原子提交。

来源文件换代只说明读取位置与文件版本改变，不自动授权删除过去已经确认的消耗。需要区分“原始文件被清理／换位置”“解析规则修正了旧贡献”“用户主动删除云端历史”；不能把新文件中没再出现的事件一律撤销。来源代次替换与长期历史保留的衔接必须明确验证。

定期或按需提供内部一致性核对：由规范事件重算部分／全部汇总，与持久结果比较；发现差异时记录影响范围并重建。原始副本丢失、项目映射变更、解析规则升级都需要可以解释的修复路径。

### 13.6 上行与下行不必使用完全相同的物理格式

上行重视小增量、来源证据、可重传和压缩；云端持久结构重视更新与索引；下行重视当前页、范围覆盖和缓存复用。可以共享语义，但分别选择合适布局。

建议保持版本化、可校验、无损的协议。先用已经有实验基础的紧凑结构与低级别 gzip 验证全流程，只有在相同输入和完整路径比较后再引入更复杂二进制格式。不能用省字段换掉缺失值、精度、来源或修订含义。

### 14.1 当前已有东西不能被简单视为从零开始

现有工作区已经有本地导入器、持久统计库、云端绑定与设备管理、共享查询引擎、账号接口和云端页面；本轮又有独立的采集器与云端处理原型。

### 14.2 建议的迁移路径

1. **冻结口径与输入契约。** 整理必须保留的原始字段、事件身份规则、项目与账号规则，准备独立预期数据。
2. **接通独立完整实验链路。** 新采集器输出实际进入新云端业务路径，返回相同查询结果；覆盖旧版累计、元数据、来源代次和多设备，而非只接受已规范化明确事件。
3. **以相同输入做新旧核对。** 比较完整事件、组成字段、Session／轮次／Agent 关系、项目／设备贡献及覆盖；将确认的旧规则问题与新实现错误分开记录。
4. **建立协议版本和升级策略。** 旧设备是继续兼容、只读已有数据、还是提示升级，需要明确；混合版本不应重复计数或降低已经确认的来源信息。
5. **迁移持久数据与人工组织。** 保留稳定身份／别名，必要时分段重建派生结果；新版本完整可用后才切换查询。
6. **迁移页面与缓存。** 复用原有页面能力，贯通设备选择和新版结果版本；缓存 schema 变化时有可恢复升级或重建策略。
7. **完成真实设备与浏览器验收后切换。** 按产品工作流处理发布，实验通过不自动成为发布授权。

### 14.3 回退需要保留什么

建议切换期间保留旧的可读完整结果，记录新旧版本边界；新路径失败可以停止切换并继续旧查询。回退不能删除原始来源、已接收的新批次或用户人工选择。

双路径核对如果同时运行，需要避免把同一数据当作两个生产来源反复计算，也要记录它的额外资源开销。正式发布后是否保留影子计算、保留多久，属于实施阶段的取舍。

### 14.4 清理规则

不可再生的身份、人工编辑、未确认上传数据、必要重放证据与可再生缓存分别管理。只有能证明后续恢复不再需要的临时结果才进入清理。既有实验目录保持历史证据，不在编写本稿时修改或重跑。

## 15. 性能与资源：怎样判断改造是否成功

### 15.1 分开计时，最终仍要测完整流程

| 指标 | 起点与终点 | 用途 |
| --- | --- | --- |
| 采集准备 | 原始完整记录可读 → 上传包持久就绪 | 判断采集和组包成本 |
| 云端新鲜度 | 原始完整记录可读 → 云端该事件可查询 | 判断采集、上传、排队、业务应用整体时延 |
| 当前页访问 | 用户请求 → 正确页面数据返回 | 判断查询与传输，不冒充正式页面绘制 |
| 页面可用 | 用户请求 → 主要内容可见且可交互 | 判断实际体验，需要正式浏览器验收 |
| 全量缓存 | 触发第二轮 → 指定云端版本的完整范围入缓存 | 判断后台补齐，不阻塞当前页 |
| 无变化刷新 | 触发同步 → 确认没有需要应用的变化 | 判断日常空转开销 |
| 修订收敛 | 最后相关来源／人工修改抵达 → 各查询结果一致 | 判断多端融合和版本发布 |

不同阶段可能流水重叠；将分开实验中的中位数直接相加，既不是实测总时间，也不保证上下界。

### 15.2 已有目标与不能擅自扩大的部分

你此前选择了首次补齐后的通常可见目标：本机约 2 秒、云端约 10 秒；访问端仍服从你设置的同步时机，用户主动等待的间隔不能算作系统处理超时。你另要求了 100k 输入已经在云端时，首次完整云端构建在 15 秒以内，后续实验已在对应范围通过。

仍需确定：正式验收使用的数据规模、设备数量、平台与网络条件，“通常”如何统计，以及页面可用和全历史缓存分别采用什么目标。建议先把同一真实输入的完整链路跑通，再据实提出承诺；不要把原型最短样本当成所有设备的固定速度。

### 15.3 工作量应随什么增长

建议的性能原则：

- 日常追加主要处理新增字节和受影响事件，而非全部历史。
- 无变化不读取整份日志内容，也不重编码全部会话；目录校验仍可能随文件数增长，应低频、有界并独立计量。
- 元数据改名、项目人工修改、额度更新有各自的变化路径，尽量不触发原始用量重解析。
- 批次按字节、记录数和受影响工作集设上限；网络并发、压缩并发和云端写入并发分别控制。
- 近期／活跃任务优先，但长期历史不能饿死；记录最老待处理年龄与补齐进度。
- 首次全量、复杂的继承修正、较大项目关系拆分会触及较多数据，应明确范围并分段处理，不虚构常数时间。

### 15.4 资源与长期增长

建议测采集进程 CPU、实际内存、磁盘增长、无变化开销、休眠恢复后的负载；也测云端请求、CPU、读写量、存储与重建成本。浏览器测缓存体积、下载量、交互阻塞与重复访问。

规模不能只看事件数：10 万事件分布在少量还是大量任务、日期、项目、模型、来源副本中，会影响索引与查询；一个长行或一个大任务也可能成为局部压力点。多设备原生数据、重叠副本比例和设备子集筛选都应进入测试。

### 15.5 成本思考

现有实验可提供具体请求和读写证据，但不能直接推成长期账单。实际月成本取决于每日新增量、查询频率、缓存命中、保留期限、重建频率与当前套餐剩余额度。

建议在不增加大量测量开销的前提下记录这些量，用观察到的实际使用分布建立月度估算。首次导入与日常增量分开；不把一次全量构建成本乘以每次刷新，也不因已有付费计划就忽略存储增长。

## 18. 我建议的工作优先级与完成标准

### 18.1 先锁住功能契约
