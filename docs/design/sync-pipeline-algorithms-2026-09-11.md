## 1. 目标与优化顺序

用户已明确根目标是将本地面板改造为多设备云端面板，支持分别／融合查看。全流程为各采集端采集原始记录，转成约定的数据结构，通常实时传到云端；访问端再按用户设置从云端同步。效率是贯穿改造的质量要求，采集器、解析器和同步环节应各自承担清楚的职责。

设计目标：**在保证统计语义、数据完整性与可恢复性的前提下，使日常工作量主要随新增和修正的数据增长，控制峰值内存，并复用已经完成的计算。**

优化顺序：

1. 消除随全部历史增长的重复扫描、解析、编码、去重和查询工作。
2. 让每个阶段能从持久进度继续，失败仅重做未提交的小批次。
3. 限制批次、并发与队列容量，使新数据不被历史补齐长期阻塞。
4. 根据实际负载比较编码、压缩与存储引擎，综合延迟、CPU、内存、磁盘、网络和云端请求成本选择。

原始新增字节必须被读取和辨认，首次全量也必须处理全部历史；这些成本不能通过改名为“缓存”而消失。“尽可能最优”以测量和复杂度为依据，不声称存在已经证明对所有负载都最优的实现。

访问端沿用原有自动／手动刷新和间隔行为；第一次近期、第二次全量共用同一个初始化进度。采集端上传独立运行。访问端只读云端，不指挥采集机器。UI 样式不在本次范围内。

## 3. 阶段之间传递什么

```text
原始 JSONL
  → 采集器：发现变化、附上持久采集身份与来源位置、安排有限的读取任务
  → 解析器：继承来源标识、语义解释、识别消耗、更新本机标准事件
  → 持久变更日志：记录本次实际改变的事件和元数据
  → 同步器：合并尚未发送的变化、封装批次、通常实时上传
  → 云端：幂等接收、处理跨来源重复、持久保存标准数据
  → 按用户设置同步到访问端：快照缺块 + 此后的变化
  → 访问端：增量入库、索引查询、展示
```

- 原始 JSON 的语义解析在采集端完成；云端和访问端只校验、解码和应用标准数据。
- 用户最新提出由采集器主动标识来源。候选采用首次初始化生成的持久 collector_id，采集数据先附来源封装，再交给解析器；长期设备来源 ID、云端绑定 ID、事件 ID 和传输批次 ID 分开。具体生命周期见[协议补充 3.0 节](sync-protocol-contract-2026-09-11.md#30-最新设计方向采集器先标识解析器继承来源)。
- 本机查询在解析事务提交后即可使用结果，上传失败不阻塞本机。
- 同步器不从头查询历史以“寻找变化”；变化由写入方明确产生。
- 云端不为每次页面筛选重新解释日志。云端接收后的去重属于多来源合并，不能省略，但应在数据变化时执行。
- 原始文件仍由 Codex 管理，不增加一份永久保存聊天正文的原始采集副本。读取任务持久保存位置和状态即可。

## 4. 核心数据结构

### 4.1 同一语义，多种物理表示

共享标准事件的字段、身份、修订与统计规则；本机数据库、云端数据库、传输包和浏览器缓存不必使用完全相同的物理格式。

| 结构 | 关键字段 | 用途 |
| --- | --- | --- |
| `source_cursors` | source_id、file_identity、generation、committed_offset、parser_version、state | 保存最近一次已提交的完整记录边界和解析上下文 |
| `source_observations` | observation_id、source_id、generation、record_position、event_id、source_revision、evidence | 保留来源与同一记录的修订，支持复制、重解析和纠错 |
| `events_current` | event_id、canonical_revision、标准事件字段、质量、当前有效状态 | 每个逻辑事件当前可计数的唯一结果 |
| `turn_state` | thread_id、turn_id、explicit_record_count、legacy_state | 控制显式记录与旧累计记录之间的替代关系 |
| `threads` / `thread_edges` | thread_id、title、metadata_revision；parent、child、edge_type | 元数据与 fork／子 Agent 关系独立更新 |
| `projects` / `project_group_members` | 原项目身份、路径、来源；group_id、project_id | 默认独立，合并只改变分组关系 |
| `change_log` | local_seq、entity_type、entity_id、source_revision、operation、payload | 持久记录变化，直接驱动同步 |
| `pending_entities` | entity_type、entity_id、latest_local_seq、priority | 合并未封装的同一实体修改，避免重复排队 |
| `outbox_batches` | batch_id、stream_epoch、lane、lane_seq、content_hash、bytes_ref、ack_state | 保存已经封装的批次，断网和重启后复用 |
| `cloud_changes` | cloud_seq、entity_type、entity_id、canonical_revision、operation、before_scope、payload | 向访问端提供稳定的增量流 |
| `snapshot_manifests` / `cache_progress` | generation、base_seq、分块清单、范围、校验、已应用集合、各阶段游标 | 表达近期和全量的覆盖、断点与完成条件 |
| `summaries` / `query_cache` | 精确范围、指标、版本、依赖范围 | 保存可重建的加速结果 |

数据结构不等于必须立即建立十二张大表：小型状态可合并存储，只有查询和事务边界需要的索引、日志才物化。特别是来源审计与页面热查询分开，避免每次查询连接全部来源副本。

### 4.2 标准事件

```text
event_id                  稳定逻辑身份
canonical_revision        云端当前结果的单调修订；本机维护本机修订
thread_id, turn_id, response_id
occurred_at_ms            UTC 毫秒；展示时再按用户时区分桶
origin_device_id          实际执行机器；证据不足时为空
project_id, model_id, effort
input_tokens, cached_input_tokens, cache_write_input_tokens
output_tokens, reasoning_output_tokens, total_tokens
kind                     显式记录或旧格式来源
quality_flags            缺字段、身份不确定、来源冲突、继承不确定等
```

Token 保留精确整数，缺失用 `null`，零用 `0`，二者不混淆。传输基线采用十进制字符串；以后采用二进制时也必须保留无损整数与独立的空值表达。时间戳只表达事件时间，不决定修订新旧。

标题、机器名称、项目完整路径和关系存元数据表，通过 ID 引用。改标题不重写整项任务的所有消耗事件。上传设备、执行设备分别记录，不能互相替代。

### 4.3 身份与修订的边界

1. 有可靠 response 标识时，在本项目用户数据域中沿用响应身份去重。同一响应复制到其他机器后，事件 ID 不改变。
2. 没有响应标识时，先用已确认的逻辑来源、来源代次和记录位置确定 observation 身份。Token 数值不进入这个身份，否则一次数值修正会变成新增消耗。
3. 不同来源的 observation 只有在来源谱系或记录匹配证据足够时才归并为同一 event；仅凭内容相同、时间接近或谁先上传，不足以保证正确。弱匹配沿用经核对的旧统计规则并标记不确定，不能宣称已经保证完全去重。
4. 来源修订只在同一来源 epoch 内比较。不同机器的自增序号和时钟不可直接比较；云端为合并后的结果分配自己的 canonical_revision。
5. 对于确实在 A 本机产生并由 A 采集的记录，标准事件生成时记录原始执行设备 A，并在后续中转中保留。上传凭据已经能够识别绑定设备，不应将正常采集记录笼统标为未知。只有缺少原始来源的特殊历史才进入未知归属；用户已接受保留全局消耗并支持带“用户指定”标记的手动批量归属。

上述第 3 项及第 5 项的来源缺失边界需要用样本验证，不能仅凭存在理论上的复制可能就判定用户实际数据已失去归属。上传设备和原始执行设备的区分在[协议补充](sync-protocol-contract-2026-09-11.md)中进一步说明。

## 5. 采集与解析算法

### 5.1 采集器：变化集合 + 低频校验

- 首次按目录分批发现历史；先处理活跃来源和近期来源，旧历史进入低优先队列。
- 文件变化通知只负责将 source_id 放入去重集合；同一文件的连续通知合并为一个待处理任务，不每次通知都全盘扫描。
- 对已知活跃来源保留短周期尺寸／身份检查；启动、唤醒、通知错误和低频巡检时补做目录发现。可疑目录分批校验，控制每次 I/O 预算。
- 通知是快速提示，不是唯一正确性依据。Node 官方明确说明 `fs.watch` 有跨平台、重命名和网络文件系统差异，因此必须保留补查路径：[Node 文件监听限制](https://nodejs.org/api/fs.html#caveats)。
- 维护 `queued/running/dirty_again` 状态：处理期间又有变化，结束后继续读取新尾部，避免既丢通知又并发解析同一来源。
- 不将整个源文件复制进内存。采集与解析之间传递来源及字节区间，读取时以有限缓冲流式交接。

### 5.2 解析器：按来源有序，有限事务提交

```text
领取 source_id
校验文件身份、代次、已提交位置
固定本次目标 EOF
从 committed_offset 开始读取
    流式识别完整记录；保留尚未结束的尾部
    解释记录，产生标准 observation 和元数据变化
    达到字节／事件／时间预算时：
        BEGIN
        更新 observations 和受影响的当前事件
        更新受影响的轮次状态、元数据和统计
        为实际变化写 change_log 与 pending_entities
        保存该完整记录边界对应的 offset + parser state
        COMMIT
    让出执行时间，再继续下一批
```

游标、解析上下文、当前数据和待同步变化在同一事务提交。崩溃发生在提交前，仅重读这一小批；发生在提交后，同步器仍能找到变更。不能先推进游标、后写事件。

解析上下文保留当前任务、轮次、模型、推理强度、项目、累计 Token 高水位、旧快照重复判定、继承边界和待补关系。它们需要跨批次延续，不能每批从零计算累计差额。

单个来源保持顺序；不同来源可以有限并行解析，但数据库提交使用明确的写入所有者。并发数由瓶颈测量调整，不按 CPU 核心数无条件启动同样数量的重任务。

### 5.3 控制原始 JSON 解析成本

- 先保留现有完整 JSON 解析与整数处理作为语义基线。
- 优化候选是结构化的选择性 JSON 解析：识别顶层类型，对用量、任务、轮次和关系提取必要字段；跳过聊天与工具正文的对象构造。
- 即使忽略正文，也必须正确识别引号、转义、嵌套、跨块 UTF-8、跨块数字和完整记录边界。不能用字符串包含测试或正则匹配来决定某条记录是否产生 Token。
- 新增字节仍需线性扫描，但可以降低无关对象分配和遍历开销。该候选只有在与基线逐项结果一致、且真实样本测量更快后才采用；手写解析器不预设比 V8 更快。
- 长行用分段缓冲或增量 tokenizer，避免每收到一小块都复制全部未完成行。有限批次只限制内存，不截断或默默丢掉长记录。无法处理的记录必须保留可恢复位置并报告质量状态。
- `session_index.jsonl` 也维护独立游标，标题更新只写对应 thread 元数据。

### 5.4 文件改写与解析器升级

普通追加走快速路径。截断、替换、发现中段改写或解析规则升级时，对受影响来源建立新代次并重解析；旧有效数据继续供查询，新结果校验完成后切换，并输出真实的差异。

不能把“文件不存在”直接转换为历史删除。低频完整校验与必要重解析可能是 O(来源字节数)，这是异常／维护成本，应单独报告，不伪装成恒定时间。无法检测任意同尺寸同时间戳改写的快速检查，也不能被宣称为完整内容校验。

## 6. 去重与汇总：更新时维护，查询时复用

### 6.1 受影响集合

单条变化先定位 event_id 的来源候选和对应轮次；只重算该事件的有效版本。若某轮首次出现显式 usage 记录，才重新处理该轮旧 token_count 的排除关系。显式记录撤回时也重新检查该轮，不能只支持单向切换。

副本完全一致时只补来源关系，不增加消耗，也不发布无意义的新 canonical_revision。来源冲突时保留冲突状态，按已定义的证据、解析规则兼容性和完整度确定当前结果；不会以不同机器的墙钟时间作为唯一胜负依据。

父子／fork 关系迟到时，使用按 parent_id 建索引的待补集合，只重算受影响的依赖；必要时会影响整个后代子图，复杂度应按实际受影响范围计算，不能承诺每次都是 O(1)。

### 6.2 修正的事务规则

```text
old = 当前有效结果
new = 按来源证据和规则解析出的新有效结果
如果 old 与 new 的可查询内容相同：只更新必要的来源状态
否则：
    从 old 所属的精确汇总中撤回旧贡献
    向 new 所属的精确汇总加入新贡献
    更新当前事件、质量计数和数据版本
    记录包含旧／新影响范围的变化
```

这适用于 Token 修正、机器归属补齐、项目纠正和事件时间修正。删除后重试也只撤回一次。不可对重传数据重复执行“加 Token”。

### 6.3 哪些结果可预计算

- 为确实高频的范围建立稀疏汇总，例如总量、任务自身总量、UTC 时间桶的 Token 加和；不建立所有维度组合的完整数据立方体。
- 汇总维护有效值数量、缺失数量、异常数量及各 Token 项的精确和，防止把 `null` 当零。缓存命中率保存分子和分母，查询时计算，不平均已有百分比。
- 时间桶拼接只在边界完全匹配时使用；用户时区或自定义范围的边界部分查原事件，保留 DST 和非整点时区语义。
- distinct 任务／轮次数不能直接相加。固定范围可维护成员引用计数；任意筛选范围使用有索引的精确 distinct 查询或精确成员集合合并。
- 每次修正同时影响旧、新两个范围；查询缓存按时间、维度、关系和设置版本失效。进度、心跳或无数据变化的同步不使统计缓存失效。
- 单条整数合法不代表总和不会超出 SQLite 整数范围。大总和使用精确分段累计／BigInt 路径，不能回退浮点数。SQLite `sum()` 存在整数溢出行为：[SQLite 聚合函数](https://sqlite.org/lang_aggfunc.html)。

## 7. 同步器：持久增量、不可变批次与有限并发

### 7.1 从变化直接产生传输任务

解析事务写 `change_log`，并将 `(entity_type, entity_id)` 的最新未封装修订登记到 `pending_entities`。同步器沿索引领取变化，不读取所有任务和所有事件计算哈希。

尚未封装时，同一实体的连续修订可合并为最新绝对状态；已经封装的批次不能原地修改。后续修订进入新批次。事件 upsert 传完整的当前标准值，不传“再加 20 Token”这种依赖严格重放顺序的算术指令。

删除分为来源撤回、纠错使事件失效和用户主动删除历史，不能统一为“采集文件不见了就删”。尚未发布的新增又被撤回可以合并，但接收端已经持有的事件需要明确的撤回／删除版本。

### 7.2 批次格式

候选传输包由以下部分组成；协议版本号待最终设计时分配。

```text
header:
    schema_version, producer_id, stream_epoch
    lane, lane_seq, batch_id
    codec, entity_count, uncompressed_bytes, content_hash
payload:
    必要元数据与包内字典
    event_observations / event_upserts
    metadata_upserts / relation_changes
    withdrawals / tombstones
```

包内字典只减少重复值；业务 ID 保持稳定，不依赖字典项在另一个包中的位置。首次引用的元数据随同传送，避免事件到了以后逐项请求项目、模型或任务信息。字典、事件数量和解压后字节数都设上限。

一个封装批次只编码、压缩、计算内容校验一次，持久保存最终字节及发送状态。断线重试直接读取该批次的字节，不再 JSON.parse 整个任务、重建全部历史或重新压缩。载荷按批次独立存放，内存最多持有有限个在途批次。

### 7.3 新数据优先与防止历史饿死

- 新变化和首次历史回填使用两个有界通道：`live`、`backfill`。它们共享来源修订规则，但分别维护传输进度。
- 历史按有限批次推进，新事件保留处理和上传机会；使用带最低历史份额的加权调度，避免一直活跃时旧历史永远不能完成。
- 历史补齐期间，每批提交完成后即可被上传；不等待整个采集扫描结束。
- 上行可以有限并发发送独立批次，但同一来源解释仍有序。更高 source_revision 先到后，迟到的旧修订不会覆盖它。
- 不用一个必须等待所有历史缺口的全局上行序号阻塞新事件。每条 lane 单独维护已接收集合／连续确认前缀；来源的新旧由实体修订判定。
- 解析、编码、传输、云端应用都有容量反馈。积压时减少历史预取，将队列放在磁盘，不能无限扩大内存或启动无限并发。

起始实验参数可从较短的合并窗口、数百 KiB 的未压缩批次、少量在途请求开始；具体数值通过基准选择。通常实时上传意味着新变化很快进入传输，不意味着每条事件单发一次 HTTP 请求，也不由访问端的刷新间隔决定。

### 7.4 云端幂等接收

云端先验证身份、协议、上限和包校验。以 `(producer_id, stream_epoch, lane, lane_seq)` 及 batch_id 标识请求：

- 同一身份与相同内容的重复批次返回既有结果。
- 同一身份却不同内容属于协议冲突，不能用“最后写入者获胜”吞掉错误。
- 只更新确实更高版本的来源 observation，对其影响的事件执行合并，生成 cloud_changes 和状态变化。
- 当前事件、相应 cloud_changes 与已应用批次标记必须处于同一原子提交边界。大包拆成有界提交单元，不能把部分应用的整个包宣称为已完成。
- 区分 `durably_received` 和 `applied`。小增量尽量直接应用；大历史可排队，但持久接收状态必须有可恢复载荷。访问端只使用已经应用的数据。
- 本机在明确可恢复／已应用确认前保留相应持久任务。失败重试使用退避和服务端 Retry-After，并允许新上传批次与历史故障分别调度。

云端不信任客户端提供的用户归属，也不接受跨用户事件 ID 作为访问授权。校验发生在每批次，避免为每个字段或事件新增网络往返。

## 8. 云端历史与访问端两轮加载

### 8.1 保存当前状态、短增量与可复用快照

云端保存当前标准事件，cloud_changes 提供其后的变更；后台将已经应用的变化合并成不可变、可校验的快照分块。多个访问端复用同一份已完成快照，不为每位访问者扫描并打包一次全部历史。

候选快照采用按时间分区、固定大小上限的稳定分块。大分区可按持久页标识拆分。更新只重建脏页；页分裂只改变关联页面和索引，避免一次早期插入使所有后续块重新编号。标题和项目元数据独立分块。

每份清单记录：

```text
generation_id, base_cloud_seq, schema_version
所有数据与元数据分块的 ID、校验、大小、事件数量、时间范围
活跃任务所需分块的索引／范围
每个来源的采集和上传覆盖状态
可续传的变化范围及清单有效期
```

**一致性构造**：以上一份完整快照为基础，将云端变化合并到固定的 C0；复制修改过的页，复用未改页。所有新对象持久保存后才原子发布清单指针。不能在可变当前表上边分页边假装得到同一时刻的完整快照。

首次构建快照有 O(N) 成本；此后压实成本与脏页和变化有关，后台有预算，不把这项开销隐藏为零。云端标准事件无需因此导出或上传用户原始 SQLite 文件。

### 8.2 第一次近期，第二次全量

1. 首次加载固定一个清单 G 和基线 C0。下载活跃任务及最近 30 天需要的块和元数据，建立本地索引与近期覆盖状态。
2. 第一轮需要追上快照后的近期变化时，使用绑定该范围的变化游标；云端必须检查变化前和变化后的范围，使从范围内移出的事件也被正确撤回。
3. 第一轮结束后等待下一次用户设置的自动或手动触发。此时补齐同一基线中尚未应用的所有块；不会立即自行启动第二轮。
4. 第二轮再应用 C0 之后的全域变化至本轮固定的 B2。此前已经应用的近期版本保留，旧基线记录不能覆盖更高 canonical_revision。
5. 全部必需块、元数据和变化均提交后，才记录全量覆盖和全域游标 B2。之后每次同步按全域游标领取增量。

`recent_cursor`、`full_cursor`、`applied_chunk_ids` 分别保存。第一轮收到较新的序号，不代表其前面的全部历史已经齐全。时间范围变更、活动任务集合变更和删除都属于范围同步协议，不能只过滤变更后的 occurred_at。

某些来源尚未上传完时，“已缓存云端在 G/B2 已提供的全部数据”与“所有采集来源历史完整”分别记录。第一阶段的任务详情需要其任务和关系依赖；尚未覆盖的旧事件明确为未加载，不能算成零。

清单或增量保留期过期时，重新取得基线；可复用且校验匹配的块继续使用，无法证明复用安全的范围重建。旧缓存保留到替换范围提交完成，避免失败后页面丢失已有历史。

### 8.3 断点与无变化刷新

每个批次在缓存事务中提交数据、相应统计和进度。仅下载完成不推进“已应用”状态；崩溃后从已提交块／游标继续。

全量已完成且云端无变化时，同步只需一次轻量版本查询或无变化响应，不下载事件、不解码历史、不重算统计。原有手动触发、关闭自动和运行中去重行为继续沿用；两轮初始化的新增状态在现有行为上实现。

## 9. 访问端存储与查询

### 9.1 物理存储的首选验证方向

- 本机继续优先复用现有 SQLite 表、整数处理和查询语义。
- 访问端优先验证 Worker 内 SQLite WASM 配合浏览器持久文件存储的方案，以复用 `shared/query-engine.ts`，并避免每次打开把全部历史转换成庞大的 JavaScript 对象数组。
- 当前 showcase 的 `sql.js` 已证明同一查询语义可以进入浏览器，但它的合成内存数据库不等于大规模持久离线方案。不能通过每次写入都导出整个 SQLite 文件来实现“增量保存”。
- 浏览器持久化能力、批量写入、锁竞争、冷启动和手机性能需要实测。SQLite 官方列出了不同 OPFS VFS 的不同并发与性能约束，因此具体 VFS 还不定稿：[SQLite WASM 持久化选项](https://sqlite.org/wasm/doc/trunk/persistence.md)。
- 多标签共用缓存时协调同步写入，避免重复下载和并发重复应用；数据库访问使用受支持的锁机制，并验证标签关闭／冻结后的接管。不能假设所有浏览器都支持相同的 SharedWorker 或持久化行为。
- 应用静态资源和数据库版本配套缓存，离线重开不依赖再次下载运行时。容量不足时保留已提交数据和断点，提示用户，不静默淘汰要求完整保存的历史。

若目标浏览器不能满足首选持久引擎要求，应选择经过验证的持久化适配方案并报告性能限制；不能悄悄回退为全量内存数据库后宣称所有设备等效支持。

### 9.2 索引与分页

起始索引按现有查询选定，示例：

```text
PRIMARY KEY(event_id)
(occurred_at_ms, event_id)
(thread_id, occurred_at_ms, event_id)
(origin_device_id, occurred_at_ms, event_id)
(project_id, occurred_at_ms, event_id)
候选来源：(event_id, source_id, source_revision)
变化日志：(cloud_seq)
关系：(parent_thread_id, child_thread_id, edge_type)
```

模型／推理强度索引以实际查询计划决定是否加入。索引有写入、空间和迁移成本，不为所有筛选组合盲目建索引。

时间排序等有匹配索引的列表采用稳定排序键；可用时使用 keyset 游标，避免深分页线性跳过大量前项。现有直接跳页的交互若需要保留，可维护分页锚点或继续使用有明确成本的 offset 路径，不能为了算法方便擅改 UI 行为。

任意筛选下按 Token 排序、distinct 计数和跨范围对比可能需要读取全部匹配事件；不能承诺所有查询都只处理当前页。常用范围使用物化统计，其他范围准确回退到索引筛选和聚合。

### 9.3 状态接口与界面更新

状态直接读取持久维护的计数、版本、覆盖与错误，不调用完整 summary。数据下载进度与统计数据版本分开。只在事件、元数据、关系或设置影响查询结果时更新相应查询。

解压、解码、批量入库和较重查询在 Worker 中执行；前端每次只接收当前视图所需结果。增量先完成缓存事务，再一次性通知相关视图，避免每插入一行就重新渲染和聚合。

## 10. 云端服务分工候选

仍以数据接收、保存和中转为主：Workers 承担鉴权和接口；现有 D1 可承担有索引的当前记录、变化、幂等状态与快照清单；R2 可保存不可变压缩分块；Queues 仅在历史应用和快照压实需要排队时引入。

普通页面筛选由访问端本地缓存完成。云端不承担每次交互都重新进行的统计查询，也不下发采集命令。账号额度作为独立快照实体自主上报并归并，不参与 Token 历史相加。

必须在最终实现设计中验证选定平台的事务、读写与存储限制，估算实际事件规模对应费用，再决定是否需要上述全部服务。R2 对象、D1 状态和队列之间不假设存在跨服务原子事务：先持久载荷，再发布可恢复状态；失败由幂等任务恢复，半完成对象不会进入访问端清单。

## 11. 已完成的合成编码实验

可复现脚本：[sync-codec-2026-09-11.mjs](benchmarks/sync-codec-2026-09-11.mjs)。本次原始结果：[sync-codec-2026-09-11.json](benchmarks/sync-codec-2026-09-11.json)。

```powershell
node docs/design/benchmarks/sync-codec-2026-09-11.mjs
```

环境：Windows x64，Node v24.16.0。使用 200、2,000、20,000 条合成标准事件；包括不同任务、机器、项目、缺失值和大于 2^53 的整数。每种格式预热 3 轮、测量 7 轮，轮换执行顺序，取各阶段中位数。每轮在计时之外验证解码后的完整逐值相等。

20,000 条事件的本次结果：

| 表示与压缩 | 未压缩字节 | 压缩后字节 | 编码＋压缩 ms | 解压＋解码为对象 ms |
| --- | ---: | ---: | ---: | ---: |
| 对象 JSON + gzip 1 | 9,900,833 | 1,709,006 | 49.626 | 40.099 |
| 数组行＋字段字典 + gzip 1 | 3,529,619 | 1,433,124 | 45.154 | 35.533 |
| 数组行＋字段字典 + gzip 6 | 3,529,619 | 1,326,792 | 88.198 | 33.324 |
| 数组行＋字段字典 + Brotli 4 | 3,529,619 | 1,241,024 | 51.702 | 31.457 |

解释与选择：

- 字典和数组行降低重复字段开销；在这一大批次样本上，gzip 1 的压缩体积减少约 16.1%。这不是整个项目的性能改善比例。
- 小批次没有统一赢家。例如 200 条时，对象格式接收处理约 0.344 ms，数组字典 gzip 1 约 0.550 ms；为了更小体积增加的对象重建成本可能抵消收益。
- gzip 6 在本样本上比 gzip 1 进一步减小体积，但发送处理成本接近翻倍。较高压缩级别不能直接等同于整体更优。
- 起始候选采用明确字段顺序、包内字典与低成本压缩；接收侧优先验证直接按行绑定入库，避免解码后再建立所有中间对象。不可变历史块可另行比较更高压缩收益。
- 最终格式还需与二进制字段编码、真实事件分布、数据库插入和浏览器 Worker 比较；这些属于性能选型，用户不需要逐项指定 codec。

该实验使用同步压缩只是为了分离计时，不是生产主线程实现建议。它没有测量网络、数据库、云端应用、原始 JSON 解析、浏览器或峰值内存，也不是当前 v2 完整协议的端到端基准。20,000 条是逻辑对比规模，不是建议的单次上传请求大小。

## 12. 复杂度与资源增长

记 F 为已知来源文件数，N 为有效事件数，b 为本次新增原始字节，d 为本次标准事件／元数据变化数，A 为语义修正真正影响的额外事件，M 为某次查询匹配的事件数，K 为输出行数。

| 工作 | 目标复杂度／增长关系 | 不能省略的成本 |
| --- | --- | --- |
| 日常发现与读取 | 与变化文件及 b 有关 | 低频完整发现仍为 O(F)，首次或来源改写需要重读 |
| 流式语义解析 | O(b)，并保留有限状态和批次 | 新字节必须被辨认；复杂的继承修正会扩大 A |
| 去重、有效事件和必要索引更新 | 约 O((d+A) log N)，另加同事件候选数 | 首次显式记录替代某轮旧记录、关系迟到会影响整个相应范围 |
| 打包与发送 | 与待发送的 d 和编码字节数有关 | 元数据依赖、批次固定开销、实际故障重传 |
| 云端增量应用 | 与 d、来源候选和受影响索引有关 | 多来源冲突需要做真实判断 |
| 日常访问端同步 | 游标定位与本次云端变化有关 | 游标过期时需要可恢复基线 |
| 匹配索引的详情／顺序分页 | 约 O(log N + K) | 没有匹配索引或存在额外过滤时可能读取更多行 |
| 任意范围聚合／排序 | 至少与 M 有关；需要排序时另有排序成本 | 不把任意查询承诺为 O(1) |
| 首次全量、完整重建 | O(N) 数据处理，另加索引构建成本 | 通过分批与优先级降低等待和峰值，不抹除总工作量 |
| 后台快照压实 | 与脏页、变化及清单更新有关 | 全新快照首次仍需要完整遍历 |

流水线内存预算由读取缓冲、解析批次、数据库缓存、有限个在途压缩块和当前查询结果决定；它不应因“保存了几年历史”而必须把几年的事件对象同时加载到内存。磁盘仍随保留数据量增长。

索引、来源记录、修订日志和快照的空间放大单独测量。已过增量保留期的变更可以在已有完整可恢复快照后压实，历史事件和必要来源证据按保留要求保存；日志压实不能删除真实消耗历史。

## 13. 验证计划与通过条件

### 13.1 验证工作量确实随增量增长

固定 d，依次将历史规模扩到 10,000、100,000、1,000,000 条，比较扫描行数、解析字节、编码次数、事务写入数和各阶段耗时。分别测量：

- 无变化刷新：日常路径不扫描全体事件、不下载事件数据、不失效统计结果。
- 在一个很大的旧任务中追加 1／10／1,000 条：新增处理不随该任务的全部历史线性增长，必要语义范围修正单列。
- 只改任务标题：只更新元数据，不重传该任务全部 Token 事件。
- 历史回填中持续产生新事件：记录新事件延迟与旧历史完成速度，检查优先级与公平性。
- 大量无关聊天正文、长行、半行追加：记录原始解析时间、分配和峰值内存，选择性解析与基线结果逐项一致。

原始采集 I/O、语义解析、去重更新、编码、压缩、网络、云端应用、下载、解压入库、查询、界面更新分别计时。记录事件／字节数量以及 P50、P95、P99，冷启动和已有缓存分别报告。

跨机器耗时使用同一测试驱动或带校准误差的时钟；不能简单相减不同机器的墙钟。访问端用户配置的等待时间与加载执行耗时分开报告，同时保留实际观察到的总等待。

原先讨论的本机通常 2 秒、云端通常 10 秒是正常在线场景的验收方向，需绑定机器、数据规模、网络和分位数；访问端仍遵守用户设置。这些目标尚未通过本次合成编码实验验证。

### 13.2 正确性与故障恢复

| 场景 | 必须验证 |
| --- | --- |
| 同一批次重复提交、ACK 丢失、乱序到达 | 结果与只应用一次相同；更旧修订不能覆盖新值 |
| 同一批次标识不同内容 | 明确冲突，不能静默覆盖 |
| 解析／入库／写 outbox 各边界崩溃 | 游标与事件一致；重启后无漏记、无重复计数 |
| A 的记录复制到 B，B 续跑 | 已确认的同一事件全局计一次，执行归属与上传来源分开 |
| 显式记录晚于旧累计记录到达／显式撤回 | 只调整受影响轮次，结果与正确的完整重算一致 |
| 先加载近期，再补全量，同时有修正和删除 | 旧块不覆盖新修订，最终与同一 B2 的完整基线一致 |
| 文件截断、替换、删除、移动、监听漏报 | 必要重解析可恢复；文件删除不抹除既有消耗 |
| 源机器离线、浏览器离线、退出再打开 | 保留已提交历史，覆盖和新鲜度如实表达 |
| 缓存空间不足、两标签写入、标签冻结 | 无损保留已提交状态，能恢复或清楚报告限制 |
| null、大整数、总和溢出、DST、项目合并 | 精确值和既有语义一致；合并项目不改变全局总量 |

使用现有统计规则和明确手工期望值双重核对；旧实现若存在错误，应解释差异，不能为了“与旧版一致”保留已确认的错误。只检查进程退出码或页面能打开不算通过。

实际浏览器验收遵循本项目指引，使用 CUA，不使用 Playwright。包括真实离线重开、设置间隔、手动推进第二轮、重复标签和大数据交互；Node 实验不替代这些检查。

## 14. 实施与迁移顺序候选

1. 先补齐分段观测、可核对的基准样本和错误场景，不改变统计结果。
2. 在本机实现事务内变更日志、独立 outbox、按事件／轮次更新，先消除全量同步扫描。
3. 再分离采集调度和流式解析，加入有限批次、来源检查与标题增量；选择性 JSON 解析以结果一致和实测收益为准。
4. 云端引入当前有效事件、增量流、幂等状态及可复用快照，验证多来源与故障恢复。
5. 接入访问端持久缓存和本地查询，落实两轮加载、增量、离线和覆盖说明。
6. 依据全链路测量选择 codec、批次窗口、并发、索引和压实策略，完成真实多端验收。

现有协议和缓存需要版本化迁移：保留旧数据与明确映射，不能把当前 device_id 直接当成实际执行机器。解析器升级产生的替代结果先在受影响范围重建并校验，再切换；旧客户端和新客户端共存时明确支持范围，不能让低版本来源覆盖已确认的新结果。

当前分支已有大量此前改动；实现时继续保留，按项目工作流进行。本文、需求档案和合成基准是本次设计产物；**本轮未修改产品实现、部署、提交或发布，也未宣称性能目标已经达到。**
