# 云端浏览器简化设计与实施

2026-09-13。用户已批准并完成本地实现；尚未部署。任务分支 `codex/performance-baseline-20260912`。实施、验证和测量见[在线页面交付记录](cloud-online-delivery-2026-09-13.md)。以下保留设计依据，并说明最终边界。

## 建议

**用户已明确选择：完全在线，不需要持久离线缓存。** 云端保存完整历史、负责去重和统计；浏览器获取当前页面所需结果，只保留当前会话内存中的查询缓存。不再复制整个云端实体库，也不将统计结果持久保存到 IndexedDB 或 localStorage。旧浏览器镜像已移入可复现的实验归档，生产入口只使用在线页面适配器。

这是明确的需求调整：原 [需求文档](multi-device-cloud-panel-requirements-2026-09-11.md) 第 1 节要求 recent 后 full 的访问端缓存，同时说明完整离线分析引擎不是必要功能。此前原型在保留完整镜像的前提下优化，数值仍有效，但不应将影子 generation、快照流、R2 分块等全部纳入新架构。

## HTTP 与 WebSocket

HTTP 响应支持持续分块发送。一次请求可以接收全部批次，不需要每批重新请求；浏览器用 `response.body` 增量读取，调用 `response.json()` 则会等待完整 JSON。Worker 可以直接返回 ReadableStream。[Fetch 流式读取](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch#streaming_the_response_body)、[Workers Streams](https://developers.cloudflare.com/workers/runtime-apis/streams/)

HTTP/2 在连接内支持多路流、头压缩和流控。串行 manifest 游标是应用协议造成的往返依赖，不能归结为 HTTP 必然逐批等待。[RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html#section-2)

WebSocket 适合长时间、频繁的双向消息，握手后消息开销小；HTTP 流适合一次请求后连续返回有限结果。两者都不能自动减少 SQL、需要传输的数据或浏览器写入，也都需要处理应用层中断和结果完整性。常用浏览器 WebSocket API 没有自动接收背压，大量数据下需要应用层控制消费速度；这不是说底层 TCP 没有流控。[WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API)

上一轮没有 WebSocket 对照。0.60 秒的合并页和 0.71 秒的 HTTP gzip 流，仅比较两种本地实现，不能据此判断 HTTP 与 WS 的通用快慢。流式 runner 还缓冲完整正文后解析，不是完整的浏览器渐进展示实验。

简化后的默认页面只需有限统计结果，先使用普通 HTTP 查询。大结果或导出才使用 HTTP 流。若后续需要更及时通知，可评估 SSE 或 WS 发送“结果有更新”，随后刷新当前页；不先引入连接协调服务或逐事件浏览器复制协议。只有明确的频繁双向需求或同条件实测收益，才将 WS 作为主数据通道。

## 复杂性的实际来源

改造前的浏览器同时维护实体镜像和查询结果缓存。`modules/sync/browser/cache-model.ts:23` 的状态包含 recent/full/delta、activeLease、baseline、coverage、receivedCommitSeq、appliedCommitSeq 和 staging；`data-source.ts:146` 的页面查询仍走服务端统计或已保存 DTO。

`data-source.ts:206` 的单实体读取接口在生产 `modules/web/` 和 `apps/` 页面中没有调用。项目实体是名称回退来源，可由同版本页面标签替代。当前离线行为也是复用已查询结果，不能依靠完整实体镜像计算任意新筛选。

用户需要的在线全历史查询不要求每个浏览器保存一份全部原始实体。将查看端当作复制节点，会带来清单、哈希、连续提交、落盘提升和跨标签恢复等成本。前一轮在它上面继续加快照和新缓存结构，会进一步提高维护成本。

## 建议保留、移除和收缩的职责

| 部分 | 决策 | 原因 |
| --- | --- | --- |
| 本地增量采集、可靠上传、重复批次幂等 | 保留 | 断线重传不能重复计费，设备关机后已上传历史仍应可查 |
| 云端全局去重、来源归属、精确 token、项目组织 | 保留 | 这是统计正确性与产品功能 |
| 浏览器 recent/full 镜像、manifest/entities/changes 消费 | 已移出生产代码 | 当前页面不靠完整实体副本计算 |
| 浏览器逐实体 SHA-256、staging、完整覆盖提升、实体 applied 游标 | 随镜像一起移除 | 不再承担复制整个实体库的工作；普通接口类型和权限验证保留 |
| 查询结果缓存 | 只保留内存中的一套 | 复用现有页面查询缓存，统一过期、身份和筛选隔离规则；删除持久 DTO、项目标签和账户 observation 缓存 |
| 页面读取租约 | 先收缩，后评估取消 | 当前服务端统计依赖租约固定数据版本，不能只删客户端对象 |
| 影子实体代次、R2 快照、压缩 Blob 后端 | 暂不接入 | 浏览器不复制实体后，失去默认访问路径中的用途 |
| 历史版本、变更日志与清理任务 | 逐项审计后缩小 | 一部分服务于实体复制，另一部分还服务于统计与后台一致发布 |

缩小职责不要求拆成微服务，也不要求把现有模块揉进一个文件。继续使用现有 Worker、D1、UI 和统计口径；减少需要共同维护的状态和数据副本。

## 简化后的访问流程

1. 完成现有身份与必要协议许可检查。
2. 请求当前页的统计和所需标签；必要查询可在服务端合并，明细继续分页，不把整个站点所有数据打成一个大响应。
3. 同一页的关联结果在同一个读取版本下生成，普通同范围刷新先准备当前已显示的查询，全部成功后公开新版本；同版本刷新复用原查询键。设置或自定义时间范围变化可能需要额外请求新范围。账户 observation 保持其独立更新时间，不强行与用量发布版本绑定。
4. 手动刷新重新读取当前页；无变化可复用已有结果。自动刷新复用现有间隔和窗口聚焦行为。
5. 网络暂时失败时可保留当前已显示的内存结果并标注更新时间；重新打开页面需要联网读取，不恢复离线历史。

浏览器维护页面 data、updatedAt、loading/error、可选 stale 标记和当前请求身份即可。用户或筛选切换时取消旧请求并拒绝晚到结果；注销、删除及跨标签内存失效仍需保持正确。无需实体同步的 coverage、received/applied 双水位、持久缓存 CAS 或逐批恢复状态。应用会话 Cookie 与静态资源缓存另有职责，不因取消数据离线缓存而被一并删除。

可以让接口内部取得固定读取版本，避免浏览器额外发同步初始化请求；也应避免为普通页面计算 expected entity counts 和完整 source coverage。最终通过独立 `POST /api/v3/view` 实现：只返回当前 cut、设置、设备范围对应的读取标识和到期时间；普通页面不调用旧 createRead，不计算实体数量或完整来源覆盖。创建 view 后，页面查询并发读取这个固定版本。

## 服务端不能一次删除所有版本机制

`modules/analytics/worker/executor.ts:5` 的 queryScope 实际读取 `v3_entity_versions` 并通过 lease 限定版本；写入路径也会依赖现行实体版本与发布序号。浏览器停止复制，不代表这些表立即没有读者。

第一步保留经过验证的统计执行器和固定版本语义，去除浏览器镜像。第二步将读取上下文限制在页面/短分页范围，审计只为镜像产生的日志和历史保留。更进一步的候选是对当前已发布事实表查询，后台重建时仅保留构建中与当前可见的发布代次；是否能替换现有 MVCC，需要证明来源修订、项目合并、删除和多 SQL 查询的一致性。

一个 HTTP 响应本身不保证多个 SQL 读取相同版本。合并页面查询后仍须使用现有固定版本，或经验证的一致性事务/发布代次。D1 batch 提供事务执行，但当前查询生成器有数据依赖，不能机械地把全部请求合为一个 batch。[D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)

跨请求分页需绑定明确版本或在旧版本不可用时重新加载；不能悄悄混合不同版本。删除和数据重建完成前也不得向页面公开半成品。上述正确性约束由服务端集中负责。

## 推荐实施顺序与验收

1. 已确定产品边界：浏览器完全在线，不保存完整实体或持久查询结果。旧应用数据库在切换时只清理本产品拥有的相关缓存，不影响其他站点、用户本地采集数据或云端历史。
2. 定位前轮发现的 cleanupVersions CPU 重置问题。该日志是当时观察，未在本轮重新探测线上；不能将扫描风险当成已证明根因。
3. 将浏览器改成页面查询客户端，保留旧统计与完整云端历史，移除实体镜像与持久 DTO 缓存依赖；同步调整原需求中的 recent/full 缓存条款与状态文案。复用现有 UI 和内存查询管理，云端与本地入口继续独立。
4. 合并当前页的必要查询，精简读取初始化，逐项删除没有消费者的镜像代码；验证后结束过渡，避免永久并存新旧默认路径。
5. 依赖审计后收缩服务端版本保留和清理范围；不先扩展 WS、R2 或另一套缓存协议。

验收同时检查行为与复杂性：同一批数据的统计、筛选、明细、组织和精确 token 完全一致；首次进入、刷新和切设备不产生实体镜像请求；正常访问不向 IndexedDB/localStorage 持久写入统计数据；接口/内存缓存中无其他用户数据；删除/退出后的晚到响应不复活缓存；刷新失败能保留已显示结果；不会显示半发布数据。用 CUA 实测页面新结果可见时间、请求数、响应字节和 IndexedDB 写入量。减少镜像工作是用户明确取消离线副本要求后的职责收缩，不能复用前轮完整同步速度来冒充新页面实测。

用户现已取消浏览器完整副本与持久离线缓存需求，不再将 snapshot + delta、影子 generation 或 R2 分块镜像列为默认实施候选。如果未来重新提出完整离线分析，应作为有明确价值与代价的新功能设计。

## 最终实现边界

- `modules/web/adapters/cloud.ts` 管理页面读取身份、固定版本、请求取消和共享在途请求；`modules/web/data/cloud-refresh.ts` 使用现有 React Query 为当前显示的查询准备下一版结果。这个临时步骤不保存实体或持久 DTO。
- 总览云端趋势直接使用查询结果，不再保留第二份组件内曲线缓存。用户、设备范围、删除或已撤销读取发生变化时，旧请求与旧显示状态失效。正常刷新不重建整个应用，避免丢失设置草稿和管理页选择。
- 新读取确认删除版本变化，或服务端明确拒绝旧读取时，先清旧页面与缓存；此时不应用“失败保留旧页”。普通有效读取遇到暂时 503 时，可以继续显示上次结果。
- 设置保存后的读取必须在写入之后开始，不能复用先于写入发出的读取。页面时钟随刷新推进，“今天”跨午夜时重新计算边界。
- 旧镜像的 9 个实现文件与对应测试/实验脚本在 `experiments/legacy-browser-mirror-20260913/`，独立运行，不在生产模块依赖图中。服务端实体版本、租约、变更日志及旧镜像 API 保留，其余消费者需另行审计。
- 修复了旧 epoch 清理的当前数据全表扫描；复用现有索引，不新增数据库、存储服务或迁移。
